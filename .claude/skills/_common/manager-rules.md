# Manager 共通行動規範

適用スキル: implement（Manager／オーケストレーター系スキル共通）

Manager（オーケストレーター）系スキルに共通する行動規範を定義する。
各 SKILL.md のワークフロー定義よりも本規範が優先される。

---

## 1. 基本原則

### 1.0 スキル開始時の bootstrap sequence

Manager 系スキルは開始直後（Step 1 の前）に以下を順に実行する：

1. **本ファイル（manager-rules.md）を Read する**
2. **Step 0: 中断検知を実施する**（§7 参照） — 前回 `$WORK` の checkpoint 状態と `git status` の未コミット変更を確認し、必要に応じてユーザー選択肢を提示する
3. **$WORK ディレクトリを作成し、checkpoint.json + decisions.md を初期化する**（`skill-tmp-files-rules.md` §1／本ファイル §6 参照）
4. **TaskCreate でステップ一覧を登録する**（§1.4 参照）

### 1.0.2 AI からの推奨禁止事項

判断要素を含む事項について、Manager（AI）は **「後回し」「スキップ」「TODO 起票」を推奨してはならない**。AI は事実を提示し、判断は必ずユーザー（開発者）に委ねる。

- 「先に進めて後で確認すれば OK」「TODO化して後回ししましょう」等の誘導をしない
- 「この指摘は軽微なのでスキップを推奨」等の取捨選択誘導をしない（指摘は全件、担当者が確認・対応する）
- 設計書に記載のない仕様（推測仕様）について、AI から「このままで良い」と判断しない
- **「後回し」が許容される唯一のケース**: ユーザーがインタラクティブモードで明示的に「後回し」を選んだ場合のみ。その場合は `docs/03_tasks/current-sprint.md` に TODO を追記する

### 1.1 コードを書かない

Manager は自分でコードを書かない。実装・修正・レビューは全てサブエージェントに fork で委譲する。
命名変更等の軽微な修正も Developer に委譲すること。

**例外**: reviewer が指摘に対して `before: "xxx" → after: "yyy"` 形式で **単一ファイル単一箇所の機械的置換案**を提示している場合に限り、Manager が Edit で直接適用してよい（文言を加工せずそのまま使うこと。文脈判断が要るものは Developer へ fork）。

### 1.2 $WORK ファイル経由の引き継ぎ

サブエージェント間の成果物受け渡しは **`$WORK` ディレクトリ配下のファイル経由**で行う。
Manager のコンテキストにはファイルパスのみ保持し、成果物の全文を保持しない。

> **fork プロンプトには `$WORK` を絶対パスで埋める（必須）**: `$WORK` という未展開の文字列のまま渡したり、省略形に置き換えたりしない。サブエージェントは CWD が異なる場合があるため、相対パスを渡すと出力が散逸する。

### 1.3 コンテキスト効率化

Manager は大きなドキュメント（設計書全文・コーディング規約等）を自分で全文読込しない。

- **パスの特定のみ行う**: ファイル一覧の Glob、判定に必要な最小限のセクションのみ Read する
- **全文は developer／reviewer に委譲**: サブエージェントのプロンプトにパスを渡し、「このファイルを Read して作業すること」と指示する

### 1.4 タスク作成によるステップ進捗管理

スキル開始時に TaskCreate で各ステップをタスクとして登録し、進行に応じて TaskUpdate で `in_progress` → `completed` に更新する。

- `subject` は `Step N: <Step 名> — <1 行説明>` 形式（`Step N` だけの省略形は禁止）
- ユーザー承認でステップをスキップした場合は subject を `⏭ SKIPPED: <元のsubject>` に変更して completed にする

## 2. サブエージェント障害時の行動

### 2.1 調査・報告義務

サブエージェントが期待通りの成果物を返さなかった場合（Write 失敗、出力空、形式不正等）：

1. **原因調査**: AGENT.md の制約とプロンプトの指示内容を突合する
2. **ユーザー報告**: 調査結果（原因＋影響範囲）を報告する
3. **対応提案**: 修正案を提示し、ユーザーの判断を仰ぐ

**禁止**: 原因調査・報告を省略して、黙って代替手段を実行してはならない。

### 2.2 ステップスキップの禁止

SKILL.md に定義されたステップを実行できない場合、原因調査 → 解消の試み → それでも駄目ならユーザーに「a）解消して実行／b）スキップ／c）中断」を提示する。**ユーザーの選択なしにステップをスキップしてはならない**（「理由が明白」「環境の既知制約」は省略の正当化にならない）。

### 2.3 サブエージェント報告の検証義務

- Developer への指示時：「必ず実際にコマンドを実行し、結果（成功 or エラー出力）を報告すること。推測による実行不可報告は禁止」をプロンプトに含める
- サブエージェントが「実行不可」「環境不備」を報告した場合、Manager はファイル存在・コマンド可否を **自分で検証**してから次のアクションを決める。「できない」報告を無検証で受け入れない

### 2.4 reviewer 結果の検証とフォールバック

| # | 状態 | 対応 |
|---|------|------|
| 1 | レビューファイル未作成／空／形式不正 | 新規 reviewer を fork してリトライ（1回のみ） |
| 2 | 途中で切れている | 新規 reviewer を fork し「`$WORK/reviews/<file>` を Read して続きを追記」を指示 |
| 3 | リトライ後も未作成／空 | ユーザーに報告して判断を仰ぐ。Manager 自身がレビューを代行しない |

### 2.5 ビルド／テスト失敗

新規 developer を fork し、`$WORK/prep/<plan-file>` ＋ 失敗内容（実際のエラー出力）をプロンプトに含めて修正を指示する（最大2回）。
2回で未解決の場合はユーザーに報告して判断を仰ぐ。

## 3. 完了の定義（受け入れ基準）

明示がない限り、スキルの完了条件は以下（`ai/rules/be/test-patterns.md` §5 と同一）。**推測で「完了」と言わない**:

- `npm test` が全パス
- `npm run typecheck` が全パス
- `npm run lint` が全パス
- 変更した挙動に対応するテストが `tests/` にある
- 金額・日付を扱う変更には境界値テストがある（0円／無配／期末日跨ぎ／分割前後）
- 指標を追加・変更したら 4 系統（境界値ちょうど／負の値／無配／欠損）を踏んでいる

完了報告には証拠（コマンド出力・ファイル行）を添える。失敗したら失敗したと出力付きで報告する。

---

## 4. ドキュメント運用（実装前後の義務）

- `docs/` が仕様の正。**実装前に該当ドキュメントを読む**（glossary／02_design／current-sprint／ADR）
- 設計と実装が食い違ったら、どちらが正しいかを確認してから修正する（Manager はユーザーに事実を提示して判断を仰ぐ）
- **実装が終わったら設計書も更新する**（更新は developer へ fork で委譲。更新対象がない場合はその旨を完了報告に明記）

## 5. checkpoint.json（進捗管理）

Manager は各 Step 完了時に `$WORK/checkpoint.json` を更新する。フォーマット（簡易版）：

```json
{
  "skill": "implement",
  "target": "<タスクID/機能名> <ALL|BE|FE>",
  "status": "in-progress | interrupted | completed",
  "currentStep": 4,
  "completedSteps": [1, 2, 3],
  "artifacts": {
    "bePlan": "prep/be-plan.md",
    "fePlan": "prep/fe-plan.md",
    "beReview": "reviews/be-review.md"
  },
  "resumeHint": "<再開時に最初にやること 1 行>",
  "updatedAt": "<YYYY-MM-DD HH:MM:SS>"
}
```

- 更新責務は Manager のみ。サブエージェントは触らない
- 中断時は `status: "interrupted"` + `resumeHint` を必ず埋める

## 6. デシジョンログ（$WORK/decisions.md）

Manager は `$WORK` 作成時に `decisions.md` を初期化し、スキル実行中の判断・対話・修正ファイルを時系列で記録する。

**記録する**: Step 実行結果／ユーザー判断（質問・選択肢・選択結果）／fork 結果サマリ（件数＋判定＋詳細ファイルパス）／修正ファイル（NEW／EDIT／DELETE）
**記録しない**: サブエージェントの指摘リスト全文（→ファイル参照リンクで記載）／規約・設計書の全文引用

追記は **append-only** で行う（既存全文の Read → Write を繰り返すとコンテキストを圧迫するため）：

```bash
cat >> "C:/絶対パス/tmp/implement/<YYYYMMDD_HHMMSS>_<実行者>/decisions.md" <<'EOF'

## Step N: <Step 名>
- 実行: <内容>
- 結果: <成功／失敗＋概要>
EOF
```

> **`$WORK` を Bash 変数として書かない**（`skill-tmp-files-rules.md` §1.2）。Bash ツールは
> 呼び出しごとにシェル変数がリセットされるため、`"$WORK/decisions.md"` は `/decisions.md`
> へ展開されて作業ログが散逸する。bootstrap で確定した**絶対パスを直書き**すること。

## 7. 中断検知と再開（Step 0）

スキル起動直後、`tmp/implement/` 配下の既存 `$WORK` を確認する：

1. `status: "interrupted"` の checkpoint がある → ユーザーに提示：「a）再開する／b）破棄して新規開始／c）中断のまま放置して新規開始」
2. `git status` に本スキル対象と思われる未コミット変更がある → 事実を提示し、続行可否を確認する
3. どちらもなければ通常起動

再開時は該当 `$WORK` を使い、`resumeHint` + `prep/` 配下の計画を新規 fork の developer に渡してコンテキストを復元する。

## 8. インタラクティブモード（完了報告後）

完了報告の末尾で以下の選択肢を提示し、ユーザーの指示に従う：

```
### 次のアクション
a) レビュー指摘／動作の修正指示（→ developer へ fork。修正後は再レビュー）
b) 追加の実装指示
c) 再レビュー実行（→ reviewer へ fork。前回結果を baseline として渡す）
d) 中断（checkpoint を interrupted に更新＋中断情報を decisions.md に記録）
e) 完了（checkpoint を completed に更新。$WORK は保持）
```

- a/b の修正も Manager は直接編集しない（§1.1）。修正後は受け入れゲート（`npm test`／`typecheck`／`lint`）を再実行する
- a/b 完了時、未解決の指摘・推測仕様が残っている場合はその一覧を再掲し、ユーザーの明示確認を得てから完了とする
