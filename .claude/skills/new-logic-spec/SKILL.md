`src/lib/` に入る**純粋な計算**の設計書を起こす手順。画面（`new-screen-spec`）と
違い、UI にも DB にも依存しないので**未決の技術選定に影響されずに書ける**。
software-architect が入出力を定義し、technical-writer が文書化し、
reality-checker が受入基準の網羅を判定する。

## 前提

- 引数は対象ロジック（例「③ 予想配当性向」「総合点の集計」）。
  無ければ `docs/01_requirements/scoring-requirements.md` を読んで
  設計書が無い指標を列挙し、**確認を取ってから**進める。
- 出力先は `docs/02_design/logic/<slug>.md`。

## 手順

### 1. 正となる仕様を読む

```
docs/01_requirements/scoring-requirements.md   … §0 が最優先。下の各指標表より強い
docs/02_design/logic/dividend-yield-scoring.md … 書式の見本（⑩ の実例）
.claude/rules/backend.md                       … 計算の規約
reference/legacy-web/README.md                 … 旧実装が実際にどう判定していたか
```

> ⚠️ **§0（決定事項）が各指標表に優先する。** 表に「0%〜25% → 10点」と
> 書いてあっても、③ の赤字は 0点が正。表を先に読んで §0 を見落とさない。

旧実装は**再利用しない**が、閾値の解釈で迷ったときの一次資料になる
（判定関数がすべて `>=` で書かれていた ＝ 下限以上・上限未満）。

### 2. 入出力を定義する — software-architect

Agent ツールを `subagent_type: software-architect` で起動し、次を出させる。

- **入力**: 何を受け取るか。単位（円 / 千円 / %、倍）を明記する
- **出力**: 何を返すか。**`null` を返す条件**を必ず定義する
- **型**: 金額は銭単位の整数。浮動小数点を経由しない
- **区分表**: 閾値と点数。境界値がどちらに属するかを §0.1 の規約で明示
- **例外条件**: 負の値 / 無配（0）/ データ欠損 / ゼロ除算
- **依存**: 他のロジックに依存するなら、その設計書へのリンク

**純粋関数として定義させる。** DB にも HTTP にも触らない形にする。
触る必要が出たら、それは `src/lib/db/` 側の責務なので分割する。

### 3. 設計書に落とす — technical-writer

Agent ツールを `subagent_type: technical-writer` で起動し、
`docs/02_design/logic/<slug>.md` を作らせる。

**受入基準は必ず4系統を網羅させる。**

| 系統           | 例                                                 |
| :------------- | :------------------------------------------------- |
| 境界値ちょうど | 増配率 20.0% を渡すと 9点を返す（10点ではない）    |
| 負の値         | EPS が負のとき 0点を返す                           |
| 無配（0）      | 配当額 0 かつ配当性向 0% のとき 0点を返す          |
| データ欠損     | 株価が `null` のとき `null` を返す（0 を返さない） |

- ✅ 「配当性向 25.0% を渡すと 9点を返す」
- ❌ 「正しく判定する」「適切に丸める」

旧実装と挙動が違う場合は、**差分を節として残す**
（`dividend-yield-scoring.md` §6 / §7 が見本）。後で「なぜ変えたか」が要る。

### 4. 網羅を判定する — reality-checker

Agent ツールを `subagent_type: reality-checker` で起動し、
設計書のパスを渡す。

確認させること。

- 受入基準が**そのままテストに落とせる**形か
- 4系統がすべて埋まっているか。該当しない系統は「—」と理由付きで明示されているか
- 境界値がどちらの区分に属するか、表を見ただけで一意に決まるか
- `null` を返す条件が定義されているか（「0 を返す」で済ませていないか）
- 単位が全ての入出力に書かれているか

既定は NEEDS WORK。1系統でも欠けていたら差し戻す。

### 5. リンクを張る

- `docs/01_requirements/features.md` の該当 F-xx から新しい設計書へリンク
- 新しい設計書から F-xx と `scoring-requirements.md` の該当節へ逆リンク
- 他のロジックに依存するなら相互リンク

### 6. 検証する

```bash
npx prettier --check docs/02_design/logic/<slug>.md
```

相対リンクが全て解決することを確認する。

## 完了条件

- [ ] `docs/02_design/logic/<slug>.md` が存在する
- [ ] 入出力の**単位**がすべて明記されている
- [ ] `null` を返す条件が定義されている
- [ ] 受入基準が4系統を網羅している（該当なしは理由付きで「—」）
- [ ] 境界値の帰属が一意に決まる
- [ ] F-xx と相互リンクしている
- [ ] reality-checker が合格を出した
- [ ] prettier が通る

## 落とし穴

- **各指標表をそのまま設計書に写さない。** §0 の決定が優先する。
  原典のままだと ③ と ⑨ で**赤字企業が満点**になる。
- **`null` と 0 を同じ扱いにしない。** 個別ロジックは `null` を返し、
  0 に丸めるのは総合点の集計時だけ。表示は `—`。
- **総合点の分母は常に 100。** ⑥⑨ が未実装の間は最大 80/100 になるので、
  有効指標数の併記を設計書に書く。
- **浮動小数点を経由する丸めを設計書に書かない。**
  `parseFloat` してから小数第2位で丸める、は不可。
- 実装（`src/lib/scoring/`）はこの手順ではやらない。`impl-from-spec` に回す。
