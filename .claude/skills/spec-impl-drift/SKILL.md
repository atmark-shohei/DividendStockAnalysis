docs を陳腐化させないための定期点検。**このスキルは自分では直さない。**
ズレの一覧を出すところまでが仕事で、修正は `impl-from-spec` か
technical-writer に回す。

## 前提

引数は無し（全体）か、対象サブツリー（例 `docs/02_design/ui/`）。

## 手順

### 1. 設計書側を拾う — repo-explorer

Agent ツールを `subagent_type: repo-explorer` で起動する
（`model: haiku` の読み取り専用。走査は安く済ませる）。

拾わせるもの。

- `docs/01_requirements/features.md` の機能 ID（F-xx）と、その状態
- `docs/02_design/ui/screen-list.md` の画面 ID（S-xx）と、設計書へのリンク
- `docs/02_design/**/*.md` の各設計書が主張している成果物
  （ファイルパス・関数名・API パスが書かれていれば拾う）

**結論だけ返させる。** ファイルの中身をそのまま持ち帰らせない。

### 2. 実装側を拾う — repo-explorer

もう一度 `subagent_type: repo-explorer` で起動する。

- `src/` 配下の実ファイルと、export されている関数・コンポーネント
- `src/app/` のルート（ページ・API Route）
- `tests/` のテストファイルと、テスト名

### 3. 突き合わせる

3つの表を出す。

**A. 設計書にあって実装に無い（未実装）**

| 設計書 | 主張している成果物 | 状態 |
| :----- | :----------------- | :--- |

**B. 実装にあって設計書に無い（無断実装）**

| ファイル | 中身 | 対応する設計書 |
| :------- | :--- | :------------- |

**C. 双方にあるが食い違う**

| 設計書 | 設計書の記述 | 実装の実際 |
| :----- | :----------- | :--------- |

C が最も危険。**設計書を信じて実装した別の箇所が壊れる。**

### 4. 判定させる — reality-checker

Agent ツールを `subagent_type: reality-checker` で起動し、
3つの表を渡して次を確認させる。

- 「実装済み」と書かれている設計書に、**対応するテストが実在するか**
- 🟢 完了 と書かれたタスクの成果物が実際に `src/` にあるか

「あるはず」を根拠として受け付けさせない。

### 5. 直さない

出力はズレの一覧まで。修正が必要なら次に回す。

- **A（未実装）** → `impl-from-spec`
- **B（無断実装）** → 設計書を起こすか、実装を消すかを**人に確認する**
- **C（食い違い）** → どちらが正しいかを**人に確認してから** technical-writer

## 完了条件

- [ ] 3つの表が埋まっている（該当なしなら「0 件」と明記）
- [ ] C の各行に、どちらが正しいか未確認である旨が書かれている
- [ ] 「実装済み」の主張がテストの実在で裏付けられている

## 落とし穴

- **`reference/legacy-web/` を実装として数えない。** 旧実装は参照専用で、
  再利用も修正もしない（T-008 決定済み）。走査対象から外す。
- `.gitkeep` しか無いディレクトリを「実装あり」と数えない。
- 設計書の「要確定」「🔴」マーカーは未実装で正常。B に入れない。
