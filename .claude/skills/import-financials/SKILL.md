**外部データは常に壊れている前提で扱う。** 単位違い（円 / 千円 / 百万円）や
株式分割の反映漏れは、そのまま利回りの桁違いになる。data-engineer が
検証項目を決め、minimal-change-engineer が実装する。

## 前提

- **データ源は外部 API ではない**（T-001 決定済み）。TSV ペースト /
  CSV ドラッグ＆ドロップ / 株価の手入力で完結する。
  外部 API クライアントを新規に作らない。
- 保存先は未決（T-002）。**特定の DB を前提にした実装を確定させない。**
  取り込みロジックは永続化から切り離し、純粋関数として書く。

## 手順

### 1. 実物のサンプルを用意する

取り込む TSV / CSV の**実際のサンプル**を1件用意する。無ければ止まる。
手書きの理想形でパーサを書かない — 実物には必ず想定外が入っている。

```
reference/legacy-web/README.md   … 旧実装が何を受け取っていたかの記録
.claude/rules/backend.md         … 外部データの扱い。ここが正
```

### 2. 検証項目を決める — data-engineer

Agent ツールを `subagent_type: data-engineer` で起動し、
サンプルを渡して**検証仕様**を出させる。最低限これらを含めさせる。

| 検証                                        | 落ちたときの扱い                               |
| :------------------------------------------ | :--------------------------------------------- |
| 必須フィールドの欠損 / `null`               | 記録して除外。捨てない                         |
| 単位（円 / 千円 / 百万円、`%` / 倍）        | 変換するか、判別不能なら拒否                   |
| 桁（株式分割の反映漏れで株価が10倍ずれる）  | 前期比で異常値を検出して警告                   |
| 日付（権利確定日が未来すぎる / 過去すぎる） | 範囲外は拒否                                   |
| 全角数字の混入                              | 半角に正規化する（日本語環境では日常的に入る） |
| 銘柄コードの形式（4桁固定、末尾1桁のみ英字可） | 形式違いは拒否                                 |

**設計書として `docs/02_design/logic/` に残させる。** 口頭で終わらせない。

### 3. 実装する — minimal-change-engineer

Agent ツールを `subagent_type: minimal-change-engineer` で起動する。
渡すもの: 2 の検証仕様、サンプルデータ、`.claude/rules/backend.md`。

守らせること。

- パースと検証は `src/lib/` の**純粋関数**。DB にも HTTP にも触らせない
- **金額は銭単位の整数**。浮動小数点を経由させない
  （`parseFloat` してから丸める実装を通さない）
- 取り込み結果に必ず `fetched_at` を付ける
- **検証に落ちたデータは捨てずに記録**する。原因調査に必要
- 無配（0円）とデータ欠損（`null`）を別の値として保持する
- 日時は UTC で保存する

テストは実物のサンプルから作る。理想形で作らない。

### 4. 検証する

```bash
npm test
npm run typecheck
npm run lint
```

### 5. 判定させる — reality-checker

Agent ツールを `subagent_type: reality-checker` で起動する。
渡すもの: 上の3コマンドの**実際の出力**、変更ファイル一覧。

確認させること。

- 2 の表の**全項目**にテストがあるか。1つでも欠けたら NEEDS WORK
- 0円 と `null` を区別するテストがあるか
- 浮動小数点が金額計算の経路に入っていないか

## 完了条件

- [ ] 検証仕様が `docs/02_design/logic/` に設計書として存在する
- [ ] 検証項目それぞれにテストがある
- [ ] 金額が銭単位の整数で扱われている
- [ ] `fetched_at` が付いている
- [ ] 検証に落ちたデータが記録される経路がある
- [ ] 無配と欠損が区別されている
- [ ] 3コマンドすべて exit 0
- [ ] reality-checker が合格を出した

## 落とし穴

- **`parseFloat` → 丸め は金額計算として不可。** 文字列のまま整数に
  持ち上げる。`"1,234.56"` → `123456`（銭）。
- **千円単位の決算数値をそのまま円として保存しない。** 決算短信は
  百万円単位が多い。単位をどこで吸収したかをコードのコメントに書く。
- **同じデータの二重取り込み**は DB の UNIQUE 制約（銘柄コード＋日付）で
  防ぐ。アプリ側のチェックだけに頼らない。
- 予想配当と実績配当を混ぜない。別カラム・別型で持つ。
