---

**実装が始まる前に止めるための手順。** 設計書の誤りは実装の誤りより
安く直せる。software-architect が設計の中身を、reality-checker が
受入基準の検証可能性を、独立に見る。

## 前提

引数は設計書のパス。無ければ `docs/02_design/` 配下で直近に変更された
ものを提示して確認を取る。

## 手順

### 1. 文脈を揃える

```
docs/01_requirements/features.md          … 紐づく F-xx があるか
docs/03_tasks/current-sprint.md           … 未決事項（🔴）に触れていないか
CLAUDE.md                                 … プロジェクト固有の決まり
```

**未決の技術選定（T-002 DB / T-003・T-004 認証）を前提にした設計書は
その時点で差し戻す。** 勝手に決めさせない。

### 2. 設計の妥当性 — software-architect

Agent ツールを `subagent_type: software-architect` で起動し、
次の観点で指摘を出させる。

- 責務が1つに絞れているか。他の設計書と重複・矛盾していないか
- 層の分離（`src/app/` → `src/lib/` → `src/lib/db/`）を壊していないか
- 規模に対して過剰でないか（**単一ユーザー・ローカル前提が既定**）
- 金額・日時の扱いが規約どおりか（銭単位整数 / UTC 保存）
- データ欠損（`null`）と 0 が区別されているか

### 3. 受入基準の検証可能性 — reality-checker

Agent ツールを `subagent_type: reality-checker` で起動する。
渡すもの: 設計書のパス。

判定させること。

- 受入基準が**そのままテストに落とせる**形か
- 「正しく動く」「きれいにする」「見やすく」の類が混じっていないか
- 金額・日付を扱うなら**境界値**が明記されているか
  （0円、無配、期末日跨ぎ、株式分割、データ欠損）
- 数値表示の単位・桁・欠損時の表記が決まっているか

reality-checker の既定は NEEDS WORK。合格させるには基準側に
根拠が要る。

### 4. 指摘をまとめる

重い順に並べる。各指摘に**設計書の行番号**を付ける。

| 深刻度 | 意味                                             |
| :----- | :----------------------------------------------- |
| 🔴     | 実装前に直す。このままだと誤った実装が出る       |
| 🟡     | 実装中に決めればよいが、決める人と時期を明記する |
| 🟢     | 好みの範囲。直さなくてよい                       |

### 5. 直す（依頼された場合のみ）

Agent ツールを `subagent_type: technical-writer` で起動し、
🔴 の指摘だけを反映させる。🟡 🟢 は勝手に直さない。

## 完了条件

- [ ] 🔴 が 0 件、または 🔴 がすべて修正済み
- [ ] 受入基準がすべて検証可能な形になっている
- [ ] 未決の技術選定を前提にしていない
- [ ] 指摘に行番号が付いている

## 落とし穴

- **レビュー担当に直させない。** software-architect と reality-checker の
  指摘は独立していることに価値がある。修正は technical-writer に回す。
- **既存の設計書と矛盾していないかを必ず見る。** 単体で読むと妥当でも、
  `screen-list.md` や他の設計書と食い違うことがある。
- スコアリングに触れる設計書は `docs/01_requirements/scoring-requirements.md`
  の §0（決定事項）が**各指標表に優先する**。逆に読まない。
