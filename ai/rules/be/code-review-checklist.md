# BE コードレビュー チェックリスト

ベース観点 = `ai/rules/be/` 全ファイル（coding-standards / test-patterns）。本ファイルはレビュー固有観点を集約した正本。

## 1. レイヤ・依存方向

- [ ] 依存の向きが `handler → usecase → domain ← infra` に従っているか（逆向き import がないか）
- [ ] handler に計算・業務ロジックが書かれていないか
- [ ] usecase から Drizzle（`drizzle-orm` / `src/infra` の実装詳細）を直接叩いていないか
- [ ] domain が Hono / Drizzle / Workers API に依存していないか
- [ ] パスエイリアス `@/*` が規約通り使われているか

## 2. 値の扱い

- [ ] 金額計算に浮動小数点が使われていないか（`Sen` 銭単位整数のみ）
- [ ] `as Sen` / `as Score` のキャストがファクトリ（`createSen` / `senFromYen` / `createScore`）の外に書かれていないか
- [ ] DB スキーマの金額カラムが整数型か（`FLOAT` / `REAL` 禁止）
- [ ] スコア区分の解釈が「下限以上・上限未満」になっているか（設計書と突合）
- [ ] 判定不可（`null`）を 0 に丸めていないか（丸めてよいのは総合点の集計時だけ）
- [ ] `MetricScore` の判別ユニオン契約が守られているか（矛盾状態を作るコードがないか）

## 3. エラー処理

- [ ] domain 層で throw していないか（`Result<T, E>` を返しているか）
- [ ] ドメインエラーが判別可能な `kind` を持っているか
- [ ] HTTP ステータス・日本語文言への変換が handler に閉じているか（domain に UI 文言がないか）
- [ ] API エラーレスポンスに内部情報（SQL・スタックトレース・パス）が漏れていないか

## 4. バリデーション・外部データ

- [ ] zod が handler 境界のみで使われているか
- [ ] 外部データが永続化前にスキーマ検証されているか
- [ ] 取得結果に `fetched_at` が付与されているか
- [ ] 検証に落ちたデータが捨てられずに記録されているか

## 5. 日時

- [ ] UTC で保存されているか。JST 変換が表示層以外に紛れ込んでいないか

## 6. テスト

- [ ] テストが `tests/` にミラー配置されているか（src に colocate していないか）
- [ ] domain / usecase / handler のテストが unit 系統にあるか（workers 系統に置かれていないか）
- [ ] table-driven で、テスト名から「何が壊れたか」が分かるか
- [ ] 金額・日付を扱う変更に境界値テスト（0円 / 無配 / 期末日跨ぎ / 分割前後）があるか
- [ ] 指標の追加・変更に 4 系統（境界値ちょうど / 負の値 / 無配 / 欠損）のテストがあるか
- [ ] 実 API を叩くテストがないか。モックが実物サンプル由来か

## 7. ドキュメント整合

- [ ] 型名・関数名が `docs/glossary.md` の用語と一致しているか
- [ ] 実装が `docs/02_design/` の設計書と矛盾していないか（矛盾があれば指摘として報告）
- [ ] 設計書に記載のない仕様が推測で実装されていないか（あれば「推測仕様」として報告）
