# docs 構成ルール

新しく設計書を書く前にここを読む。**単位の判断基準はこの中にあるものを使い、
毎回既存ファイルの模倣で決めない。**

## ディレクトリと単位

| ディレクトリ                 | 単位                                       | 分割しない理由・する理由                                                                     |
| :--------------------------- | :----------------------------------------- | :------------------------------------------------------------------------------------------- |
| `00_overview/`               | 横断的な関心事1つにつき1本                 | アーキテクチャ・データフローなど、特定の機能に属さないもの                                   |
| `01_requirements/`           | 要求領域ごとに1本                          | 領域内の項目が相互参照するなら分割しない（例: `scoring-requirements.md` の §0 は10指標共通） |
| `02_design/logic/`           | **不変条件・計算式を1つ持つ概念ごとに1本** | 10指標 = 10ファイル。1指標を直しても他指標に影響しないのが分割の根拠                         |
| `02_design/api/`             | 集約・リソース単位                         | `auth-api.md` / `user-api.md`。エンドポイントの粒度ではなく、扱うリソースの粒度              |
| `02_design/database/`        | スキーマ全体で1本＋関心が別なら別ファイル  | テーブル間の外部キー制約があるため分割すると整合性チェックが2ファイルにまたがる              |
| `02_design/ui/pages/`        | 画面（タブ）単位                           | ユーザーが辿る単位。索引は `screen-list.md`                                                  |
| `02_design/ui/components.md` | 複数画面から再利用する部品はここに集約     | ページファイルに書くと、画面ごとに部品の説明が重複する                                       |
| `adr/`                       | **決定1つ = 1ファイル、番号採番**          | 「なぜその選択をしたか」は機能単位ではなく決定単位が自然な粒度。複数機能にまたがってよい     |
| ルート直下（`docs/*.md`）    | ドメイン・移行全体の横断ドキュメント       | `migration-plan.md`, `domain-model.md`, `glossary.md`                                        |
| `03_tasks/`                  | スプリント・タスク一覧（時系列で更新）     | 設計ではなく進捗管理                                                                         |

## 判断に迷ったら

1. **その文書は他の何と一緒に変わるか。** 一緒に変わるものは同じファイルに置く
   （区分表を直したら必ず更新するものは、区分表と同じファイルに書く）。
2. **その文書は独立してレビュー・受入判定できるか。** できるなら分ける
   （10指標が別ファイルなのはこれが理由）。
3. **決定そのものか、決定を反映した仕様か。** 前者は `adr/`、後者は `01_requirements/` か
   `02_design/`。ADR は「なぜ」を記録し、仕様書は「何を」を記録する。決定を仕様書に
   直接書くと、後で決定を覆したときにどこを直せばいいか分からなくなる。

## `02_design/logic/*.md` の章立てテンプレート

10指標の設計書は全て同じ構成。新しい指標を追加するときもこれに従う。

```
1. 概要
2. 入出力
3. 計算ロジック（計算式）
4. スコア判定
5. 例外処理
6. 受入基準
7. 参考資料との差分と決定
8. 既存実装との対応
（実装済みになったら）実装（日付）— 何を実装したか、実装ファイルへのリンク
```

## ファイル名規則

- 小文字ケバブケース（`dividend-growth-rate-scoring.md`）
- `02_design/logic/` は `<指標名>-scoring.md`
- `02_design/ui/pages/` は `<画面名>-page.md`（例外: `criteria-tab.md` — タブという性質を優先）
- `adr/` は `NNNN-<決定を要約した短い句>.md`（4桁ゼロ埋め連番）

## 設計書と実装が食い違ったら

`CLAUDE.md`（プロジェクトルート）の方針の通り、**どちらが正しいかを確認してから**
片方を直す。無断でどちらかに合わせない。実装が終わったら設計書も必ず更新する
（陳腐化させない）。
