## 利用規約について（2026-07-29 決定）

**規約の条文は確認していない。** その前提のうえで、ユーザーが
「個人利用のためOK」と判断し、リスクを受容してこの経路を使うことを決定した。
これは「規約が自動取得を許可していることを確認した」という意味では**ない**。
単一ユーザー・個人利用（`docs/01_requirements/features.md`「未決定の前提」の
「単一ユーザー前提か」は依然未決だが、少なくとも本アプリの現在の運用は
個人利用）という利用形態を踏まえた、ユーザー自身によるリスク受容である。

**この決定が無効になる条件**（見直しのトリガー、変わらず有効）:

- 本アプリを個人利用の範囲を超えて使う（複数ユーザーへの公開、商用利用等）
  ようになった場合は、このリスク受容の前提が崩れるため**再度判断し直すこと**
- IRバンク側から利用停止・規約違反の指摘があった場合は直ちに案A
  （手動 DL＋D&D）へ切り戻す

## 背景

T-001 は「**外部 API は使わず、TSV ペースト / CSV ドラッグ＆ドロップ / 株価の手入力で
完結する**」と決めていた（`docs/03_tasks/current-sprint.md:14`）。理由はレート制限・
利用規約・費用の懸念を消すためで、その判断自体は当時の情報では妥当だった。

その後、IRバンクが**銘柄コード直指定の静的 JSON** を公開していることが分かった。

```
https://f.irbank.net/files/{code}/fy-data-all.json
```

9433 / 8306 / 7203 / 1301 の4銘柄で実測し、以下を確認した。

- 4銘柄すべて 200。構造は完全に一致し、`業績` / `財務` / `CF` / `配当` の4ブロック
- **列名がデータ自身に埋まっている**（`meta.item.年度` が列名の配列）。列順の決め打ちが不要
- **値は円の生値**。単位行の解釈が不要（NTT 売上 5,446,708,000,000 が実額と一致）
- **予想/実績が `備考: "予想"` で判別できる**。F-02 が要求していた「区分判定」が不要になる
- `robots.txt` は `User-agent: * / Disallow:`（空）＝クロール全許可
- レスポンスは `Content-Encoding: br` 固定。Workers の `fetch` は自動で解凍する

これは**API ではなく静的ファイル**であり、CSV 取り込み（F-03/F-04）で最もコストが
かかる部分（単位変換・列順・注記行・全角混入）がすべて不要になる。CSV パーサを
書くより明確に安く、かつ壊れにくい。

## 決定

**Worker から `f.irbank.net` の静的 JSON を直接 fetch する。** T-001 の
「外部 API を使わない」は、**「認証・課金を伴う外部 API を使わない」に読み替える**。
TSV ペースト / CSV D&D（F-01〜F-04）は、この経路で埋まらない項目の補完手段として残す。

> ⚠️ **2026-08-07 追記: 上記の読み替えはさらに改定されている。**
> [ADR-0011](./0011-edinet-financial-history-api.md) が「認証・課金を伴う外部API」を
> 「課金を伴う、または再利用可否が規約上不明な外部API」に改めた（EDINET APIの
> 採用のため）。最新の判断基準は ADR-0011 を参照すること。

株価は引き続き手入力（この JSON に株価は含まれない）。

## 検討した代替案

- **案A: ユーザーがブラウザで DL し、画面に D&D する** — T-001 も
  `docs/00_overview/data-flow.md` も変更不要で、既存の F-03（D&D 入力）の枠に収まる。
  不採用理由: 銘柄ごとに手作業が1回増える。1000社超を扱う前提（`.claude/CLAUDE.md`）
  では現実的でない。**取得経路以外の実装は案Aと共通**なので、規約面で問題が出たら
  パーサをそのままに前段だけ差し替えられる（下記「見直しのトリガー」）
- **案B: CSV 取り込み（F-03/F-04）を予定どおり実装する** — 方針変更が一切要らない。
  不採用理由: 同じデータに対してパーサのコストが数倍になる。単位・列順・注記行の
  解釈がすべて実装側の責任になり、IRバンク側のレイアウト変更で黙って壊れる
- **案C: J-Quants 等の公式 API を使う** — データが権威的で期間も長い。
  不採用理由: 利用登録と認証が必要で、T-001 が避けたかった依存そのもの

## 結果・影響

**楽になること。**

- 単位変換・列順の決め打ち・注記行の読み飛ばし・全角正規化がすべて不要
- 予想/実績の判別が `備考` で取れる（F-02 の区分判定ロジックが要らない）
- EPS と BPS が取れるため、**PER / PBR の手入力が不要になる**
  （株価から算出可能。⑨ MIX係数の入力が1つ減る）

**引き受けるトレードオフ。**

- `docs/00_overview/data-flow.md` の「外部データ源への自動アクセスは無い。
  レート制限・リトライの設計は不要」が**成立しなくなる**。
  ✅ 2026-07-29 更新済み — 同ファイル §0 に取り込み専用のフローを追加し、
  §1（保存フロー）とは別扱いにした
- IRバンクの可用性・レイアウト変更に依存する層が1つ増える
- **利用規約の条文は依然未確認。** `robots.txt` は全許可だが、それは規約の
  代わりにならない。2026-07-29、条文を確認しないまま「個人利用のためOK」と
  リスクを受容する決定をした（上記「利用規約について」）。**規約違反が
  無いことを保証する決定ではない。** 個人利用の範囲を超える場合は再判断が必要

**この JSON だけでは埋まらないもの（重要）。**

実績は **4〜5期しか無い**。`fy-data-all` の "all" は「全ブロック」であって
全期間ではない（`q-data-all.json` は 404、他のファイル名は 302）。

> 📌 下表は ADR の背景説明用の要約。**指標別カバレッジの正は
> [irbank-json-import.md §6.2](../02_design/logic/irbank-json-import.md)。**
> 表を更新するときは両方直すのではなく、§6.2 だけを直してここからは参照する
> 運用にすること（`/review-spec` で二重管理を指摘された）。

| 指標                               | 必要                   | 可否                                  |
| :--------------------------------- | :--------------------- | :------------------------------------ |
| ⑨ MIX係数 / ⑩ 配当利回り           | EPS・BPS＋株価         | ✅（株価は手入力）                    |
| ③ 予想配当性向                     | 予想EPS＋予想配当      | 🟡 業績ブロックに予想行がある銘柄のみ |
| ⑤ ROE平均 / ⑧ 営業利益率           | **実績5期**            | 🟡 業績ブロックが実績5期の銘柄のみ    |
| ① 増配率 / ⑦ 売上CAGR / ④ EPS CAGR | 6期                    | ❌ 配当実績4期・業績4〜5期            |
| ② 連続非減配年数                   | 最大18期               | ❌ 4期では最大3年しか数えられない     |
| ⑥ 配当維持可能年数                 | 流動資産・投資有価証券 | ❌ **項目自体が無い**                 |

> ⚠️ **③ と ⑤⑧ は同時に埋まらない。** 業績ブロックは常に5行で、そこに予想が
> 入るかは決算発表のタイミングで決まる。実績5期の銘柄（9433 / 8306）は ⑤⑧ が
> 埋まって ③ が空になり、実績4期＋予想1の銘柄（7203 / 1301）はその逆になる。
> 詳細は [irbank-json-import.md §6](../02_design/logic/irbank-json-import.md)。

**確実に埋まるのは ⑨⑩ の2指標**（いずれも株価の手入力が前提）。残りは従来どおり
手入力する。総合点は「有効指標数」の併記（`scoring-requirements.md` §0.5）で
これが読み取れる。

この経路の主な価値は指標の充足ではなく、**年度別テーブル 4〜5行 × 5列の手入力が
消えること**、および **PER / PBR の入力欄が不要になること**（株価から算出）。

**見直しのトリガー。** `/review-spec`（2026-07-28）で「誰が・いつ判定するか
決まっておらず、努力目標のまま放置されるリスクがある」と指摘された。
2026-07-29、利用規約の条文確認は「個人利用のリスク受容」で置き換える決定を
したため（冒頭「利用規約について」）、下の1点目は判定条件を差し替えた。

- **本アプリの利用形態が個人利用を超えた場合、または IRバンク側から
  利用停止・規約違反の指摘があった場合** → 案A（手動 DL＋D&D）へ差し替える。
  パーサ（`src/infra/irbank/parse-fy-data.ts`）は取得
  （`src/infra/irbank/fy-data-client.ts`）と既に分離済みなので、取得側だけ
  「ユーザーが貼り付けた JSON を受け取る」形に差し替えれば済む
- **全期間の取得手段が見つかった場合** → ①②④⑦ をこの経路に移す
  - 判定条件: `f.irbank.net` に `fy-data-all` 以外の全期間エンドポイントが
    見つかること。現状 `q-data-all.json`（404）以外は未探索
- 8306 の営業利益が `"-"` であることを実測で確認した。⑧ の金融業の扱い（🟡 保留、
  `scoring-source-comparison.md` 決定5）は、この取り込みが入ると実データで踏むようになる

## 実装時に踏む罠（実測済み）

サンプルは `tmp/irbank-samples/`（9433 / 8306 / 7203 / 1301）。

1. **同じ列でも年度によって `number` / 数値文字列 / `"-"` が混在する。**
   7203 の営業利益は 2023〜2024 が `"2725025000000"`（文字列）で 2025 以降が数値。
   `typeof === 'number'` を前提にすると別の銘柄で必ず落ちる。4銘柄・6列で実測
2. **予想年度だけ配列でなくオブジェクト。** `{"0":84,"1":"-",…,"備考":"予想"}` の形。
   `Array.isArray` で分岐しないと落ちる。全銘柄の `配当` ブロックで発生する
3. **欠損は文字列 `"-"`。** `null` ではない。**0 と混同したら利回りが壊れる**
4. **ブロック間で年度レンジがずれる。** 7203 は `業績` が 2023〜2027、`財務` が
   2022〜2026。**添字で揃えると1年ずれる。** 年度キーで突き合わせること
5. **JSON の数値は既に double。** `150.01` が来るため「文字列のまま整数へ持ち上げる」
   （`import-financials/SKILL.md:95`）が素直にはできない。銭化の方法を決めること
6. `Content-Encoding: br` 固定。Workers の `fetch` は自動解凍するが、curl で
   サンプルを取り直すときは `--compressed` が要る
