# 0012: 指標カスタマイズの区分表スケーリング方式と総合点の分母

- 日付: 2026-08-16
- ステータス: 承認

## 文脈

[design_mock](../design_mock/README.md) の試作（指標カスタマイズ画面）を設計へ反映するにあたり、
2つの未定義が見つかった。決定は
[design-mock-alignment.md](../03_tasks/design-mock-alignment.md) §3 D-2・D-3 で先にユーザーと
合意済みで、本 ADR はその決定を実装可能な形に落とす。

**D-2: 「満点となる基準値」1つから、11段（③のみ10段）の区分表をどう作るか。**
試作は指標ごとに「これで10点」となる値をユーザーに1つだけ入力させる。しかし
正典 [scoring-requirements.md](../01_requirements/scoring-requirements.md) の区分表は
10個の境界値を持つ。1値から10境界を導く方法が未定義だった。

**D-3: 選択指標が 5〜10 個のとき、総合点の分母をどうするか。**
現行 [scoring-requirements.md §0.5](../01_requirements/scoring-requirements.md#05-データ欠損は0点として合算分母は常に100)
は「分母は常に100点」と定めている。これは全10指標を採点する前提であり、
ユーザーが指標を絞れるようになると成立しない。

[ADR-0005](./0005-thresholds-fixed-for-now.md) は「閾値は当面デフォルト固定」を決定したが、
同 ADR の「追記」節に**この決定を先送りした事実**が明記されている。
本 ADR はその約束を果たすもので、ADR-0005 の「現時点ではまだ未実装」という結論
（今すぐ `bands.ts` の定数を変える、という意味ではない）を覆さない。

### 実装済みの区分表の形（`src/domain/scoring/bands.ts` 実測）

区分表の「満点（10点）」がどちら向きの境界かは指標によって違う。

| 向き                             | 対象指標      | 「満点となる基準値」の意味                                                                   |
| :------------------------------- | :------------ | :------------------------------------------------------------------------------------------- |
| **昇順**（値が大きいほど高得点） | ①②④⑤⑥⑦⑧⑩      | 最上位区分の**下限**（例: ⑤ROEは `15%以上→10点`）                                            |
| **降順**（値が小さいほど高得点） | ③予想配当性向 | 最上位区分の**上限**（`0%以上25%未満→10点`。**単調減少**であり、原典のような U字型ではない） |
| **ユーザー設定不可**（derived）  | ⑨MIX係数      | 対象外。常に `bands.ts` の定数を使う                                                         |

⑨ MIX係数が設定不可なのは試作・要件（`今後やりたいこと.md`）とも一致しており、
本 ADR で新たに決める事項ではない。

## 決定

### D-2: 比例スケーリング

**ユーザーが入力した「満点となる基準値」と、その指標のデフォルト満点境界の比から
スケール係数を求め、10個（③のみ9個）の境界値すべてに同じ係数を掛ける。**

```
scale = 基準値 ÷ デフォルト満点境界
新境界[i] = デフォルト境界[i] × scale   （i は全境界。null はそのまま null）
```

- 「デフォルト満点境界」は上表のとおり、昇順指標は最上位区分の下限、
  ③（降順）は最上位区分の上限（`25`）を使う。
- 0点区分の境界（例: ①の `0`）は `0 × scale = 0` のまま変わらない。
  境界の**間隔比**が保たれるため、11段の粗密がそのまま拡大縮小される。

**追加の制約（実装時に必ず入れること）:**

1. **基準値は正でなければならない。** `scale ≤ 0` になると境界が非単調・全て0に潰れるなど、
   区分表が破綻する（`validateBands()` の `ThresholdNotAscending` 相当で弾かれるべき状態）。
   [indicator-custom-page.md](../02_design/ui/pages/indicator-custom-page.md)（起票予定・T-080）の
   数値入力に `min` はあるが、③⑥は試作の制約表で `min: -100` になっており、**そのままでは
   0以下を許してしまう。** ドメイン側で「基準値 > 0」を追加のガードとして持つ
   （UIの `min` 表示は変更しなくてよいが、0以下は保存前に拒否する）。
2. **スケーリング後の10（③は9）境界は、保存前に必ず `validateBands()` を通す**
   （ADR-0005 が既に定めた規約。丸め誤差で境界が接触・逆転する可能性があるため）。
3. **④⑦⑧のように現状同一の定数を共有していない指標は、スケーリングも指標ごとに独立に行う。**
   `bands.ts` 冒頭のコメント「共有すると片方を直したときにもう片方が黙って変わる」と同じ理由。

### D-3: 総合点の分母 = 選択指標数 × 10

**総合点の分母は、ユーザーが選択した指標数に応じて動く（`選択数 × 10`）。
選択が5指標なら50点満点、10指標なら従来どおり100点満点になる。**

- 既存の「有効指標 N/10 を併記する」ルール（§0.5）と同じ考え方の延長。
  「有効指標 N/選択数」に置き換わる。
- **選択していない指標は、有効・無効の判定にも総合点にも一切関与しない。**
  §0.5 の「データ欠損は0点として合算」は**選択した指標の中でだけ**適用する
  （選択しなかった指標を0点として合算すると、指標を減らすほど不利になり、
  「選べる」機能の意味が無くなる）。
- ⑨ MIX係数は常に選択可能な10指標の1つとして扱う（設定不可なだけで、選択・除外は可能）。

**副作用として明記すること:** 設定の異なるユーザー間、または同じユーザーでも選択指標数が
違う銘柄同士では、**総合点を単純比較できない。** 画面（[indicator-custom-page.md](../02_design/ui/pages/indicator-custom-page.md)・
解析ダイアログ）に必ず注記を出す。

## 検討した代替案

**D-2:**

- 案B: 満点境界だけ動かし、残り9境界は固定 — 基準値を下げると表が非単調になり
  `validateBands()` に落ちる（例: ROEの満点境界を8%に下げると `8%→8点` の既存境界と衝突）。
  「なぜ落ちたか」をユーザーに説明しづらい。不採用。
- 案C: 10境界すべてをユーザーに入力させる — 試作のUI（基準値1つの数値入力）と乖離し、
  入力コストが高い。境界の単調性をユーザー自身が保証する必要があり、実装の複雑さが
  ドメイン層からUI層へ移るだけ。不採用。

**D-3:**

- 案(b) 100点へ正規化（`合計 ÷ (選択数×10) × 100`）— ユーザー間で比較しやすい見た目になるが、
  §0.5 の「欠損は0点として合算」と組み合わせると、選択数が少ないほど欠損1件の影響が
  正規化後に増幅される（5指標中1件欠損は20点減、10指標中1件欠損は10点減）。
  「比較可能に見えるが実際は比較できない」という誤解を生みやすく、不採用。
- 案(c) 総合点は常に10指標100点で計算し、選択は表示フィルタのみ — 既存ロジックを
  変えずに済むが、「各指標の評点（基準値）を自分で設定できる」という要件（`今後やりたいこと.md`）
  を満たさない。不採用。

## 結果・影響

**楽になること:** 既存の11段判定ロジック（`lookupPoints` / 各指標の `scoreByBands`）は
無改造で使える。区分表という「データ」を差し替えるだけで済み、判定コードに分岐を増やさない。

**引き受けるトレードオフ:** ユーザー間・銘柄間で総合点が単純比較できなくなる
（分母が変わるため）。UI での注記が必須になる。

**新たに必要になる実装（Phase B。依存関係は
[design-mock-alignment.md](../03_tasks/design-mock-alignment.md) §4 参照）:**

- T-079: `scoring-requirements.md` §0.5 を「選択指標数×10」の前提で書き直す
- T-080: 指標カスタマイズ画面の設計書（基準値>0のドメイン制約を明記）
- T-100: `基準値 → スケーリング後の区分表` を導出する domain 関数＋境界値テスト
  （基準値がデフォルトと同じとき、既存の `bands.ts` と完全一致することを確認するテストを含める）

**見直しのトリガー:** ユーザーからのフィードバックで「総合点が比較できないのは分かりにくい」
という声が強ければ、D-3 の案(b)（100点正規化）への切り替えを再検討する。
その場合は §0.5 の欠損合算ルールも同時に見直す必要がある。

## 追記（2026-08-22, T-100 実装時に確定）

D-2 の実装（`src/domain/scoring/band-scaling.ts`）にあたり、本文で明記していなかった
2点をユーザー承認のうえ確定させた。

- **`scaleBands()` はスケーリング後の数値を丸めない。** `新境界[i] = デフォルト境界[i] × scale`
  で得た値をそのまま境界値として返す（`validateBands()` を通すのみで、四捨五入・切り捨て等の
  整数化は行わない）。⑩配当利回りのように `bands.ts` 側が 1/100% 整数単位を採用している指標で
  非整数の境界が生じても、この関数の責務では丸めない。整数化が必要になった場合は、
  呼び出し側（usecase 層。T-101 で追加予定）で行う。
- **⑨ MIX係数（`MIX_COEFFICIENT_BANDS`）の呼び出し禁止は型では強制しない。**
  `scaleBands()` はどの `ScoreBand[]` を渡しても同じロジックで動作する（呼べてしまう）。
  「⑨は設定不可」という制約の担保は usecase 層（T-101）の責務とする。
