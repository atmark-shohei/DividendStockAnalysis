# ADR-0011: EDINET API を認証つきで、日次バッチも伴って利用する

- ステータス: ✅ 採用
- 日付: 2026-08-07
- 関連: [ADR-0007](./0007-irbank-json-direct-fetch.md)（「認証・課金を伴う外部APIは
  使わない」の初出）、[ADR-0010](./0010-yahoo-chart-endpoint.md)（EDINETを一度
  却下している。定期実行禁止の初出）、
  [edinet-history-import.md](../02_design/logic/edinet-history-import.md)（本ADRに
  依存する設計書）、
  [balance-sheet-derivation.md §7.3](../02_design/logic/balance-sheet-derivation.md)
  （「EDINETのXBRLを採るかは別途ADRで決める」と予告済み）

## 背景

[docs/01_requirements/features.md:98-101](../01_requirements/features.md) は次のとおり
**決定済み（`[x]`）**の記述を持つ。

> - [x] 外部 API からの自動取得を将来行うか →
>       **2026-07-28 決定。** IRバンクの静的 JSON に限り Worker から直接取得する
>       （ADR-0007）。**認証・課金を伴う外部 API は引き続き使わない**

この文言は ADR-0007 の決定（「T-001の『外部APIを使わない』は『認証・課金を伴う外部API
を使わない』に読み替える」）をそのまま引き継いだものである。

[edinet-history-import.md](../02_design/logic/edinet-history-import.md) は、④ EPS CAGR・
⑦ 売上高CAGR が要求する実績6期のうち IRバンク（最大5期）で埋まらない年度、および
⑥ 配当維持可能年数が要求する流動資産・投資有価証券（IRバンクのどの経路にも無いことが
`balance-sheet-derivation.md` §7.3 で実測済み）を、金融庁 EDINET の有価証券報告書から
取得する設計である。

**EDINET API v2 はすべてのエンドポイントで Subscription-Key（無料・本人登録制）が
必須**（書類一覧 `documents.json` すら401で弾かれる。同設計書 §2.1 実測済み）。
これは上記の決定に**そのまま反する**。

### ⚠️ ADR-0010 が EDINET を一度却下している

[ADR-0010](./0010-yahoo-chart-endpoint.md) の「検討した代替案」は EDINET を案Cとして
次の理由で却下していた。

> **案C: EDINET（金融庁）** — 見送り。財務データは取れて二次利用も認められているが、
> **株価が無い**。配当も有報からの抽出になり **XBRL のタクソノミ解析が要る**。
> 公開路線に舵を切るなら再評価する価値がある

**株価が無いという理由は変わらない**（本ADR・本設計書の対象外は変わらず配当・株価）。
しかし「XBRLのタクソノミ解析が要る」は、`edinet-history-import.md` §2.3 の実測で
**無効化された**。EDINET API v2 は 2024年4月以降、XBRLをタブ区切りCSVに変換済みの
ZIPを `type=5` パラメータで返す。生XBRLの名前空間解析・タクソノミ揺れの吸収は不要で、
「経営指標等の推移」という標準タグ（`SummaryOfBusinessResults`）を機械的に読むだけで
5期分のEPS・売上高が取れることを2社（9433・1301）で確認済みである。

**ADR-0010 が想定していなかった追加の非対称性もある。** 同ADRの決定#3は
「ユーザーの操作1回につき1銘柄1リクエスト。一覧の全銘柄を一括更新する機能・定期実行・
クローリングは作らない」と定めている。しかしEDINETには銘柄コードから書類IDを直接引く
エンドポイントが無く（`documents.json` は日付単位の一覧しか返さない）、1,000社規模で
実用的な速度にするには**日付側から1回だけ走査して `edinetCode → docID` のインデックスを
事前構築する**設計が必要になる（`edinet-history-import.md` §4.4）。これは決定#3が
禁じる「定期実行・クローリング」に該当するため、**決定#3自体も改定が必要**。

## 決定

1. **`docs/01_requirements/features.md:98-101` の文言を改定する。**

   > 変更前: 「認証・課金を伴う外部 API は引き続き使わない」
   > 変更後: 「**課金を伴う、または再利用可否が規約上不明な外部 API は使わない**」

   EDINETは①課金が発生しない、②官公庁（金融庁）が公開する一次情報のAPIである、
   ③二次利用が明示的に許諾されている、の3点で改定後の文言に適合する。**判断基準を
   「認証の有無」から「課金の有無・二次利用の可否の明確さ」に置き換える。** 認証
   そのもの（Subscription-Key）は、費用も規約上の不明瞭さも伴わない限り禁止事由と
   しない

2. **EDINET API v2 を、`edinet-history-import.md` が定める範囲（④⑦の古い年度・
   ⑥の流動資産と投資有価証券）に限って利用する。** 株価・配当・予想値は対象外の
   まま（IRバンク・Yahoo Financeが引き続き担当）

3. **[ADR-0010](./0010-yahoo-chart-endpoint.md) 決定#3を改定する。**

   > 変更前: 「ユーザーの操作1回につき1銘柄1リクエスト。一覧の全銘柄を一括更新する
   > 機能・定期実行・クローリングは作らない」
   > 変更後（EDINET経路に限る）: 「**docIDインデックスの構築に限り、日次バッチ
   > （Cloudflare Workers の Cron Trigger）による全社ぶんの事前走査を許可する。**
   > 財務データそのものの取得（`fetchHistory`）は引き続きユーザーの操作1回につき
   > 1銘柄1リクエストとする。Yahoo Finance 経路の「定期実行・クローリングは作らない」
   > は変更しない」

   docIDインデックスは**書類の存在確認**であり、財務データそのものの取得ではない。
   EDINETは公的機関の公開APIで二次利用も明示的に許諾されているため、この非対称な
   扱いが正当化できる（Yahoo Financeの非公式エンドポイントには適用しない）

4. **個人利用に限る**（ADR-0007・ADR-0010と同じ立場）。このアプリを不特定多数に
   公開しない。広告・課金を含む収益化をしない

5. **Subscription-Key は環境変数として扱う。** `.dev.vars`（ローカル）/
   `wrangler secret put`（本番）で `EDINET_API_KEY` として渡し、コード・ログ・
   エラーメッセージに値を出さない（`.claude/rules/security.md`）

6. **取得層とパース層を分ける**（ADR-0007・ADR-0010と同じ）。規約面・API仕様面で
   取得できなくなったときに前段だけ差し替えられるようにする

⚠️ **条文の適法性を確認したわけではない**（ADR-0007・ADR-0010と同じ立場）。
弁護士等の確認は取っていない。ただし EDINET は金融庁が運営する法定開示システムであり、
`edinet-history-import.md` §2.1 で確認したとおり**キー発行自体が公式に用意された
利用者登録フロー**である点で、IRバンク・Yahoo Finance（非公式エンドポイントを
黙って叩く形）より規約面の不確実性は小さい。

## 検討した代替案

- **案A: J-Quants API（有料）** — 却下。ADR-0010でも一度検討済み。Standard
  プラン（月3,300円）なら10年前までのEPS・売上高が構造化データで取れ、パースも
  容易だが、**継続課金が発生する**。改定後の`features.md`の文言（「課金を伴う…
  外部APIは使わない」）にそのまま抵触する。個人の趣味プロジェクトの規模を超える
- **案B: 古い年度を手入力のままにする（現状維持）** — 却下。①②④⑦が要求する
  6期以上前のデータ、⑥が要求する流動資産・投資有価証券を、1,000社超の規模で
  手入力し続けるのは非現実的（`.claude/CLAUDE.md`の登録規模を踏まえる）
- **案C: EDINETを使うが日次バッチは作らず、都度1,000日分を走査する** — 却下。
  銘柄ごとに独立して日付を走査すると 1,000社 × 約20営業日 = 20,000リクエストに
  なり、ユーザーが取り込みボタンを押すたびに待たされる。ADR-0010決定#3を
  「そのまま守る」ことより「対象を絞って例外化する」ほうが実害が小さいと判断した
  （決定3）

## 結果・影響

**楽になること。**

- ④ EPS CAGR・⑦ 売上高CAGRが、遡及修正の無い銘柄で埋まるようになる見込み
  （`edinet-history-import.md` §3・§4.3）
- ⑥ 配当維持可能年数の残り2項目（流動資産・投資有価証券）が自動で埋まる見込み
  （同 §3。ただしタグは未検証）
- 1,000社超の手入力（古い年度の財務データ）が大きく減る

**引き受けるトレードオフ。**

- **`features.md`の判断基準を書き換える。** 「認証の有無」という機械的で分かりやすい
  基準から、「課金の有無・二次利用可否の明確さ」という多少の判断を要する基準に
  変わる。次に外部APIを検討する人は、認証の有無だけで機械的に判断できなくなる
- **日次バッチ（Cron Trigger）という新しい実行形態が入る。** これまでの取り込みは
  すべて「ユーザーが操作した瞬間だけ動く」設計だったが、docIDインデックスの構築は
  ユーザー操作と無関係に定期実行される。監視・失敗時の扱い（アラートは出すのか、
  黙って次回に持ち越すのか）は `edinet-history-import.md` の未決事項（§8-5）として
  残っている
- **Subscription-Keyという、このアプリで初めて扱う秘密情報が増える。** キー未発行・
  失効時にEDINET経路だけが機能しない設計にする必要がある
- **ZIP展開の依存追加が要る**（Cloudflare Workers の `DecompressionStream` は
  ZIP非対応）。`fflate` 等の追加が必要（`balance-sheet-derivation.md` で既知）
- **遡及修正（§2.6実測）への対応コストを引き受ける。** 同じ年度でも提出時期に
  よって数値が異なりうるため、`edinet-history-import.md` §4.3 の突き合わせロジック
  （案A＋C）が必要になった。単純に「最新を信じる」だけでは済まない

**この経路でも埋まらないもの。**

- 株価・配当・予想値（引き続きIRバンク・Yahoo Finance）
- 決算期変更（変則決算）企業の④⑥⑦（`edinet-history-import.md` §1.2でスコープ外）
- 米国基準採用企業（タグ体系が未確認）

## 見直しのトリガー

次のいずれかが起きたら本ADRを再検討する。

- **公開・収益化を検討する**（個人利用の前提が崩れる。最優先のトリガー）
- EDINET APIの利用規約が改定され、個人利用や二次利用の位置づけが変わる
- EDINETがSubscription-Keyの発行を停止・有料化する
- 日次バッチが1,000社規模で実用的な時間・リクエスト数に収まらないことが実測で
  分かった場合（`edinet-history-import.md` §9 着手順2）。その場合は決定3の
  「日次バッチ」自体を見直す
- ⑥のBSタグ（流動資産・投資有価証券に対応する要素ID）が実測できず、⑥のスコープが
  本ADRの想定より縮小する場合（`edinet-history-import.md` §6 の残課題）

## ⚠️ 見直しトリガー発火（2026-08-16・未解決）

**本ADRの決定4「個人利用に限る。このアプリを不特定多数に公開しない」の前提が変わった。**

[ADR-0013](./0013-multi-user-auth-small-scale.md) で、少人数（家族・友人規模）が
各自アカウントを持つ認証の導入を決定した。本ADRが**最優先の見直しトリガー**として
挙げていた「公開・収益化を検討する（個人利用の前提が崩れる）」に該当しうる。

なお ADR-0013 は「不特定多数への公開・収益化はしない」ことも同時に決めており、
`SIGNUP_MAX_USERS` による人数上限も設ける。**「公開」に当たるかは解釈の余地がある**が、
本ADRが最優先トリガーとして名指ししている以上、明示的に判断すべき事項として残す。

- **これは未解決の課題であり、本ADRの結論はまだ更新していない。**
- 決着は `docs/03_tasks/design-mock-alignment.md` の **T-107**
- **T-107 が決着するまで、認証機能を本番デプロイしない**（設計・実装は進めてよい）
