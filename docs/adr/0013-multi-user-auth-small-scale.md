# 0013: 少人数向けの自前メール＋パスワード認証を導入する（招待制は採らない）

- 日付: 2026-08-16
- ステータス: 承認
- 関連: T-003 / T-004（認証の要否・公開範囲）、[ADR-0005](./0005-thresholds-fixed-for-now.md)、
  [ADR-0007](./0007-irbank-json-direct-fetch.md)、[ADR-0010](./0010-yahoo-chart-endpoint.md)、
  [ADR-0011](./0011-edinet-financial-history-api.md)

## 文脈

[今後やりたいこと.md](./今後やりたいこと.md) が、メールアドレスとパスワードによる
アカウント作成・ログイン、ユーザーごとのポートフォリオと指標カスタマイズ、
銘柄登録画面の管理者限定を求めている。これを実現するには認証が要る。

**T-003（認証の要否）・T-004（公開範囲）は 2026-07-26 の起票以来ずっと未決だった。**
`docs/03_tasks/todo-list.md` では一時 🟢 完了と誤記されていたが、
`current-sprint.md` は一貫して 🔴 未決としており、実態は未決だった（2026-08-16 に訂正済み）。

### 制約1: 「ローカル専用だから認証不要」は既に成立していない

- `wrangler.jsonc` に実在の D1 データベースID（`a46f0e15-...`）と Cron Trigger があり、
  **デプロイ前提の構成**になっている
- `workers.dev` は URL を知られれば誰でも到達できる
- 現状、**銘柄の登録・更新・削除は誰でも実行できる**（`POST /api/companies` 等に保護が無い）
- 一方 EDINET の管理用エンドポイント2本だけは `X-Admin-Token` 共有シークレットで
  保護されている（`src/handler/app.ts`。未設定なら 503）。
  **「守るべき操作がある」という認識は既にコードに存在する**

### 制約2: データ源のADR3本が「個人利用」を前提にリスク受容している

| ADR      | データ源      | 前提                                     | 見直しトリガーの記載                               |
| :------- | :------------ | :--------------------------------------- | :------------------------------------------------- |
| ADR-0007 | IRバンク      | 「個人利用前提でのリスク受容」           | 「**複数ユーザーへの公開**、商用利用等」           |
| ADR-0010 | Yahoo Finance | 「個人利用に限って直接叩く」             | 同様                                               |
| ADR-0011 | EDINET        | 「不特定多数に公開しない。収益化しない」 | 「**公開・収益化を検討する（最優先のトリガー）**」 |

いずれも「条文の適法性を確認したわけではない」と明記したうえでの、
**ユーザー自身によるリスク受容**である。複数ユーザーが各自アカウントを持つ形にすると、
この3本の前提が変わる（§結果・影響 を参照）。

## 決定

**少人数（家族・友人規模）が各自アカウントを持つ形の、自前のメール＋パスワード認証を導入する。
招待制は採らない。**

### 1. ロールは guest / user / admin の3つ

| ロール              | 閲覧できる画面                      |
| :------------------ | :---------------------------------- |
| guest（未ログイン） | 検索・評価基準                      |
| user                | ＋ ポートフォリオ・指標カスタマイズ |
| admin               | ＋ 銘柄登録                         |

- **「ログインせずとも銘柄の検索は可能」**（今後やりたいこと.md）を満たすため、
  認証ミドルウェアは**全体には掛けない**。保護するルートを個別に指定する
- **銘柄データ（`companies` 等）は全ユーザー共有のマスタデータ**として扱う。
  admin だけが登録・更新・削除でき、user と guest は読むだけ。
  ユーザーごとに持つのはポートフォリオと指標設定だけ
- 試作（design_mock）の「デモ表示」ロール切替コントロールは**出荷しない**。
  ロールは必ずセッションから決まる

### 2. サインアップは自由登録。ただし人数上限を設ける

**招待コードは実装しない**（運用の手間に見合わないため）。代わりに、
**登録できる人数の上限**と**登録受付の ON/OFF** を環境変数で持つ。

- `SIGNUP_MAX_USERS`: 登録可能な最大ユーザー数。到達後の登録は 403
- `SIGNUP_ENABLED`: 登録受付そのものの ON/OFF。必要なときだけ開ける

これは招待制ではない（誰に配るコードも無い）が、**「気づいたら知らない人が登録していた」を
防ぐ最小限の歯止め**になる。§結果・影響 のとおり、この歯止めが無いと本 ADR の
「少人数」という前提が技術的に何も担保されなくなる。

**最初に登録したユーザーを admin にする。** 2人目以降は user。
admin を後から昇格させる画面は当面作らない（必要になったら D1 を直接更新する）。

### 3. パスワードハッシュは Web Crypto の PBKDF2、**イテレーション数 = 10,000**（2026-08-17 実測・確定）

⚠️ **`auth-api.md` の「bcrypt / argon2 でハッシュ化する」は Workers では実現できない見込み。**
ネイティブモジュールが載らないため。`worker-configuration.d.ts` に
`SubtleCrypto.deriveBits` の存在は確認済みで、**PBKDF2 を採用**。

#### 実測（T-063。`tests/integration/pbkdf2-iteration-benchmark.test.ts`）

workerd（`@cloudflare/vitest-pool-workers` 経由の miniflare）上で `crypto.subtle.deriveBits`
を実行し、3回計測の中央値を取った。

| イテレーション数          | 所要時間（中央値） |
| :------------------------ | :----------------- |
| 10,000                    | 4ms                |
| 50,000                    | 17ms               |
| 100,000                   | 34ms               |
| 210,000（OWASP 最小推奨） | 71ms               |
| 310,000                   | 105ms              |
| 600,000（OWASP 推奨値）   | 398ms              |

**この Cloudflare アカウントは Workers Free プラン**（ユーザー確認済み、2026-08-17）。
Free プランの CPU 時間上限は歴史的に**リクエストあたり10ms**（正確な現在値は
Cloudflare ダッシュボード Workers → Plan → Limits で要確認。時期により変更されうる）。

⚠️ **OWASP 最小推奨（210,000回）でも 71ms かかり、10ms 上限を大きく超える。**
ハッシュ化以外（JSON解析・zod検証・Honoルーティング）の CPU も同じ予算を消費するため、
Free プランの制約下で OWASP 推奨水準を満たすイテレーション数は無い。

#### 決定: イテレーション数 = 10,000（明示的なリスク受容）

- **費用（Paid プランへの移行、月$5）より、Free プランを維持することを優先**する
  ユーザーの決定（2026-08-17）
- 10,000回（実測4ms）は**OWASP 最小推奨（210,000回）の約1/21**であり、
  DB が漏洩した場合のオフライン総当たり耐性が大きく下がる。
  **これは意図的なリスク受容であり、見落としではない**
  （[ADR-0007](./0007-irbank-json-direct-fetch.md)等が「個人利用のリスク受容」を
  明示するのと同じ扱い）
- ソルトはユーザーごとにランダム生成し、ハッシュと同じ行に保存する
  （`users.password_salt`。[schema.md](../02_design/database/schema.md)）
- **`users.password_iterations` に実際に使ったイテレーション数を保存する**
  （[schema.md](../02_design/database/schema.md)）。Paid プランへ移行して
  イテレーション数を引き上げたとき、**既存ユーザーのハッシュは古い回数のまま
  検証でき、次回ログイン成功時に新しい回数で再ハッシュする**（段階的移行。
  全ユーザーに再登録を強制しない）
- **平文・可逆暗号で保存しない**、**ログ・エラーメッセージに出さない**
  （`.claude/rules/security.md`）

### 4. セッションは D1 のテーブル ＋ HttpOnly Cookie

- `sessions` テーブルに保存し、Cookie は `HttpOnly; Secure; SameSite=Lax`
- **JWT は採らない。** 失効させにくく、ログアウトと管理者によるセッション破棄が
  素直に書けないため
- 有効期限を持ち、期限切れ行は削除する

### 5. 既存の `X-Admin-Token` は残す（役割を分ける）

EDINET の管理用エンドポイント2本（`/api/admin/edinet/...`）は**機械向け**で、
Cron や手動運用から叩かれる。ユーザーセッションを持たないため、
**共有シークレットによる保護を維持する**。

- 画面から使う admin 機能（銘柄登録）＝ **ロールで保護**
- 機械から使う運用エンドポイント ＝ **`X-Admin-Token` で保護**

両者を統合しない。統合すると Cron からの呼び出しにセッションが必要になる。

### 6. パスワードリセットは実装しない（当面）

メール送信基盤が要り、少人数運用では手間に見合わない。
忘れた場合は D1 を直接更新する。`auth-api.md` の該当の未決コメントはこの決定で閉じる。

## 検討した代替案

- **案A: 単一ユーザー＋パスワード保護**（アカウント作成は初回1回だけ）—
  データ源ADR3本の「個人利用」前提をそのまま維持できる唯一の案で、
  ポートフォリオ・指標カスタマイズ・admin限定もすべて実現できた。
  **不採用の理由: 「各ユーザーごとにポートフォリオを組みたい」という要件そのものを満たせない**
  （今後やりたいこと.md の見出しが「各ユーザーごとに」で始まっている）
- **案B': 招待制**（招待コードを持つ人だけ登録できる）— 登録者を確実に限定でき、
  データ源ADRの「不特定多数に公開しない」を技術的に担保できた。
  **不採用の理由: ユーザーの明示的な指示**（2026-08-16）。運用の手間に見合わないと判断。
  代わりに §決定2 の人数上限で最小限の歯止めを置く
- **案C: 誰でも登録できる公開サービス** — 今後やりたいこと.md の記載を最も素直に満たすが、
  データ源ADR3本すべての前提が完全に崩れ、IRバンク・Yahoo・EDINET の使用可否から
  再検討が要る。実質的に別プロダクトへの転換になるため不採用
- **案D: 認証を入れない** — 明示要件（ログイン画面・アカウント作成画面の新規作成）を
  満たさず、かつデプロイ済みのため誰でも銘柄を書き換えられる状態が残る。不採用
- **better-auth 等のライブラリ導入** — `.claude/CLAUDE.md` の原本が候補に挙げていたが、
  本 ADR の規模（メール＋パスワード、セッション、3ロール）なら自前で十分小さく収まる。
  `~/.claude/rules/security.md`「新しい依存を追加する前に既存で足りないか確認する」に従い、
  **当面は自前**。OAuth・2要素認証が要るようになったら再検討する

## 結果・影響

### ⚠️ データ源ADR3本の見直しトリガーが発火した（未解決）

**本 ADR は認証の設計を決めるものであり、データ源のリスク受容を更新するものではない。**

ADR-0007 は「本アプリの利用形態が個人利用を超えた場合、再判断が必要」、
ADR-0011 は「公開・収益化を検討する」を**最優先の見直しトリガー**として明記している。
少人数とはいえ複数ユーザーが各自アカウントを持つ形は、これらの前提を変える。

したがって次のいずれかが必要になる。**これはユーザー自身が判断すべきリスク受容であり、
本 ADR では決めない。**

1. 新しい利用形態（少人数・非商用・宣伝しない）で改めてリスクを受容し、
   ADR-0007 / 0010 / 0011 に追記する
2. データ源を公式API・有料データへ置き換える検討に入る

**この判断が済むまで、認証機能を本番デプロイしない**こと（設計・実装は進めてよい）。

### 楽になること

- 銘柄の登録・削除が無防備な現状が解消される
- ポートフォリオ・指標カスタマイズがユーザーに紐づけられ、
  [ADR-0012](./0012-indicator-customization-scaling-and-denominator.md) の
  「ユーザーごとの区分表」が実装可能になる

### 引き受けるトレードオフ

- **自前認証の保守責任を負う。** レート制限、セッション失効、タイミング攻撃対策
  （認証失敗の応答を一定にする）を自分で実装・維持する
- **人数上限を超えた運用に弱い。** admin 昇格画面もパスワードリセットも無いため、
  ユーザーが増えると D1 の直接操作が必要になる
- **PBKDF2 のイテレーション数を10,000に抑えたことで、OWASP 最小推奨（210,000）の
  約1/21のハッシュ強度になった。** DB 漏洩時のオフライン総当たり耐性が低い。
  Free プラン維持（月$0）を優先した明示的なリスク受容（§決定3）

### 見直しのトリガー

- 利用者が「少人数（家族・友人規模）」を超える
- 公開・収益化を検討する（データ源ADRのトリガーと同じ）
- パスワードリセット・OAuth・2要素認証が必要になる（ライブラリ導入を再検討）
- Workers の CPU 制限でログインが失敗するようになる（ハッシュ方式の見直し）
- **Workers Paid プランへ移行する（月$5）。** そのときは `password_iterations` を
  600,000（OWASP推奨値。実測398ms）まで引き上げる。`schema.md` の
  `password_iterations` 列により既存ユーザーは再登録不要（§決定3）
- `users` テーブルの行数が増え、DB 漏洩時の実害が無視できなくなる
  （少人数の前提が崩れる兆候。上とも連動）
