## 1. 概要

**未ログインでも到達できる、認証の入口。**
ヘッダーの「ログイン」ボタン、またはログイン必須画面へのアクセス時のリダイレクトから開く。

**この画面がしないこと:**

- パスワードのハッシュ化そのもの（サーバー側 = `auth-api.md` の責務。フロントは
  平文パスワードを送信するだけで、ハッシュ化を模倣・実行しない）
- 検索・評価基準の閲覧制限（この2画面はログイン無しで使える。§1参照。
  この画面を経由しなくても使える）
- パスワードリセット（[ADR-0013](../../../adr/0013-multi-user-auth-small-scale.md) §決定6により
  当面実装しない）

**1つのコンポーネント・2つのURL。** ログイン（`/login`）とアカウント作成（`/signup`）は
同じレイアウト・セグメント切替コンポーネントを共有するが、**状態ではなく別URL**として実装する
（[screen-list.md](../screen-list.md) §1「ログインとアカウント作成は1つの画面の2モード。
ただし URL は分ける」）。セグメントコントロールのクリックは、内部 state のトグルではなく
`navigate('/login')` / `navigate('/signup')` のページ遷移。

## 2. URL・クエリパラメータ

**[screen-list.md](../screen-list.md) §3.5 が正。**

| パラメータ | 意味                                         |
| :--------- | :------------------------------------------- |
| `redirect` | 成功後に戻る画面のパス。**相対パスのみ許可** |

- `/login` タブから `/signup` タブへ切り替えるとき、**`redirect` を引き継ぐ**
  （`/login?redirect=/portfolio` → 「アカウント作成」タブ押下 →
  `/signup?redirect=/portfolio`）
- **オープンリダイレクト対策。** `redirect` が `/` で始まらない、または `//` で始まる場合
  （プロトコル相対URLでの外部リダイレクト）は無視して `/` に倒す。
  検証は `routes.ts` の純関数に置く

## 4. 入力検証

| 項目                                   | クライアント側                                                                                 | サーバー側                                                                                              |
| :------------------------------------- | :--------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------ |
| メールアドレス                         | 形式チェック                                                                                   | **必須**（クライアントだけに頼らない）                                                                  |
| パスワード（アカウント作成時）         | **8〜128文字**（[auth-api.md](../../api/auth-api.md) §POST /api/auth/signup と同じ下限・上限） | **必須**                                                                                                |
| パスワード（ログイン時）               | 空でないこと（下限は課さない。既存アカウントの古いパスワードを弾かないため）                   | **必須**                                                                                                |
| パスワード（確認、アカウント作成のみ） | パスワードと一致すること                                                                       | **サーバー側では検証しない**（確認欄はUXのためのクライアント専用チェック。サーバーに2回送る必要はない） |

- 全角文字が混入したメールアドレスは正規化しない（メールアドレスの全角→半角変換は
  誤変換のリスクが高く、既存の数値入力の全角正規化とは性質が違うため対象外とする）

## 5. エラー表示

### 5.1 ログイン（`/login`）

| 状況           | 表示                                                     |
| :------------- | :------------------------------------------------------- |
| 認証失敗       | 「メールアドレスまたはパスワードが正しくありません」     |
| 試行回数超過   | 「しばらく時間をおいてからお試しください」               |
| サーバーエラー | 「ログインできませんでした。時間をおいてお試しください」 |

> ⚠️ **「そのメールアドレスは登録されていません」と出さない。**
> アカウントの存在有無が漏れる。認証失敗はすべて同じ文言にする。

### 5.2 アカウント作成（`/signup`）

| 状況                                     | 表示                                                               |
| :--------------------------------------- | :----------------------------------------------------------------- |
| メールアドレスが登録済み                 | 「そのメールアドレスは既に登録されています」                       |
| 登録上限到達（`SIGNUP_MAX_USERS`）       | 「現在、新規登録を受け付けていません」                             |
| 登録受付停止中（`SIGNUP_ENABLED=false`） | 同上                                                               |
| パスワード（確認）が一致しない           | クライアント側で送信をブロックし、当該欄の下に表示（送信前に防ぐ） |
| サーバーエラー                           | 「登録できませんでした。時間をおいてお試しください」               |

> ⚠️ **ログインとは逆に、アカウント作成では「登録済み」を明示してよい。**
> 新規登録フローでメールアドレスの存在有無を隠すと、ユーザーが
> 「既存アカウントでログインすればよい」と気づけず、無限に登録を試みてしまう。
> これは一般的な UX 上のトレードオフであり、ログイン失敗時の匿名化とは別の判断
> （既存アカウントの**パスワード**は一切要求・検証しないため、乗っ取りの手がかりにはならない）。

- **登録上限・受付停止は同じ文言にする。** 「上限に達した」と「意図的に締めている」を
  ユーザーに区別させる必要はない（運用側の内部事情）

## 6. セキュリティ

- パスワードを `localStorage` / `sessionStorage` に保存しない
- 入力値をログ・エラー計測サービスに送らない（パスワード確認欄も含む）
- 送信は POST のみ。GET のクエリに載せない
- ログイン・登録成功後は `redirect` のパスへ戻す。**リダイレクト先を外部 URLにしない**
  （§2 のオープンリダイレクト対策）
- **パスワードのハッシュ化はサーバー側でのみ行う**（Web Crypto の PBKDF2。
  [ADR-0013](../../../adr/0013-multi-user-auth-small-scale.md) §決定3）。
  フロントエンドは平文パスワードを1回 POST するだけで、ハッシュ化のロジックを持たない
- footnote の「パスワードはハッシュ化して保存され、平文では保持されません」は
  **UI上の約束であり、実装（サーバー側のハッシュ化）と一致していることを
  実装時にレビューで確認する**

## 7. 読み込み中・送信中の表示

- 送信ボタンは送信中 `disabled` にし、二重送信を防ぐ（`CompanyForm` の `importing` と同型）
- 通信の成功・失敗が確定するまでフォームの入力値は保持する（失敗時に再入力させない）

## 8. 受入基準

- ✅ ログイン失敗時、メールアドレスの存在有無が判別できない（§5.1）
- ✅ 連続失敗でレート制限が働く（429相当。文言は §5.1 のとおり）
- ✅ アカウント作成で7文字以下のパスワードを送信すると、送信前にクライアント側で
  エラーが表示される（サーバーへの通信を待たない）
- ✅ アカウント作成で8文字以上のパスワードは送信できる。ログイン時は
  7文字以下のパスワードでも（既存アカウントとの一致検証自体は）拒否されない
- ✅ ログイン・登録成功後、`redirect` のパスに戻る。`redirect` 省略時は `/`
- ✅ `?redirect=https://evil.example.com` を渡しても外部に飛ばない（`/` に倒れる）
- ✅ `?redirect=//evil.example.com`（プロトコル相対）も同様に `/` に倒れる
- ✅ パスワード・パスワード確認の値がネットワークログ・アプリログに残らない
- ✅ アカウント作成で、既に登録済みのメールアドレスを送信すると
  「そのメールアドレスは既に登録されています」と表示される（ログインの匿名化文言とは異なる）
- ✅ 登録上限到達時、新規登録フォームの送信が拒否され、上限到達の文言が出る
- ✅ 「アカウント作成」タブへの切替時、`redirect` クエリが引き継がれる
- ✅ 送信中はボタンが `disabled` になり、二重送信されない
- ✅ `frontend/` に色・サイズの直値が無い（[design-tokens.md](../design-tokens.md) §6）
