# 取り込み結果のレビュー 仕様書（人間が判断する箇所の提示）

> 2026-07-30 起票。ユーザーの要求「取得したデータが怪しい場合は、人間が判断するようにしたい」
> を仕様に落としたもの。前提となる取り込みの仕様は
> [irbank-json-import.md](./irbank-json-import.md)。

## 1. 概要

銘柄コードから財務データを取り込んだあと、**人間が判断しなければならない箇所を
特定して画面に提示し、その場で直せるようにする**ロジックを定義する。

このアプリは投資判断の材料を出す。取り込んだ値が黙って間違っているのが最悪の失敗で、
次に悪いのが「怪しいことは分かるが、どこが怪しいのか分からない」状態である。
現状は後者になっている（§2）。

**この設計書がやらないこと。**

- 値の自動補正・自動除外はしない。株式分割の反映漏れと記念配当・業績急回復は
  機械的に区別できない（[irbank-json-import.md](./irbank-json-import.md) §5.3）。
  **判断は人間が下す。システムは判断すべき箇所を漏らさず示すところまで。**
- 新しい検証項目を増やすことは主目的ではない。既に検出しているものを
  **人が行動できる形にする**のが主目的。ただし誰も検出していない穴（§4）は埋める。
- 投資判断そのものの自動化はしない（`CLAUDE.md`）。

## 2. 現状の欠陥（この設計書が直す対象）

### 2.1. 診断が件数に潰れていて、場所が伝わらない

`ImportDiagnostic` は `block` / `fiscalYearKey` / `column` / `raw` を持っている
（`src/domain/company/financial-source.ts:20`）。API 応答にもそのまま載っている
（`src/handler/dto/irbank-import.ts:35`）。

ところが画面は `summarizeDiagnostics()`（`frontend/components/CompanyForm.tsx:91`）で
**件数に潰している**。

```
3件はデータなし扱いにしています。2件は値を採用したまま、前年比の急変・丸めなどを記録しています
```

「値を採用したまま記録しています」と言われても、**どの年度のどの列か分からないので
人間は何も判断できない**。持っている情報を捨てているだけであり、
検出機構が働いていることの通知にしかなっていない。

### 2.2. 取り込みが手入力を黙って消す

`buildRowsFromImport()`（`CompanyForm.tsx:127`）は自身のコメントで
「手入力の入力先である空行を消さないため」差し込み方式にしたと書いているが、
実際に保持しているのは**空の枠だけ**である。

`byYear` に無い年度は `emptyRow()` に戻り、`DEFAULT_ROWS`（6）より古くて
取り込みにも無い年度は `extraRows` の条件（`byYear.entries()` 由来）に入らないので
**行ごと消える**。

①②④⑦ は取り込みで**構造的に埋まらない**（[irbank-json-import.md](./irbank-json-import.md) §6.2）。
つまりこの機能は手入力とセットで使う前提であり、「年度を追加」で足して埋めた行が
2回目の取り込みで消えるのは、機能の目的そのものと矛盾する。

### 2.3. 「なぜ `—` なのか」が分からない

年数が足りずに指標が判定不能になった場合、画面には空欄が並ぶだけで、
**あと何年入れれば出るのか**が分からない。①②④⑦ は必ずこの状態になるので、
最も頻繁に人の判断を要する箇所なのに何の案内も無い。

## 3. 判定ロジック

### 3.1. 置き場所と分割

判定は**素TS の純粋関数**に置く（`.claude/CLAUDE.md`「計算・判定は必ず domain へ」）。
`CompanyForm.tsx` に条件分岐を書かない。

| 判定                   | 置き場所                              | いつ確定するか                                 | 誰が実行するか                     |
| :--------------------- | :------------------------------------ | :--------------------------------------------- | :--------------------------------- |
| セル単位の警告（§3.2） | `src/domain/company/import-review.ts` | **取り込んだ時点で確定**。手入力では変わらない | handler が計算し、DTO に載せて返す |
| 指標単位の不足（§3.3） | `src/domain/scoring/coverage.ts`      | **入力中に変わる**。手入力で埋まっていく       | 画面が入力のたびに再計算する       |

**分ける理由。** セル警告は「外部データがこう来た」という事実なのでサーバー側で
確定できる。一方、指標の充足は手入力で変化するので、サーバーに問い合わせ直すのは
不自然になる（1文字打つたびに `fetch` することになる）。

⚠️ 後者は frontend から domain を実行時 import する必要があり、
現在 [ADR-0008](../../adr/0008-frontend-domain-runtime-import.md) は
`deriveMarketMultiples()` に限って許可している。**対象の拡張が要る。**
§8-1 の未決事項として扱う。

### 3.2. セル単位の警告

```ts
/** 診断1件を、画面のどのセルの話かに解決したもの */
interface CellWarning {
  /** 決算年度。`fiscalYearKey`（'2026/03'）の先頭4桁。解決できなければ `null`（§6） */
  readonly fiscalYear: number | null;
  /** 元のキー。画面に併記する（§3.4）。年度に解決できなくても捨てない */
  readonly fiscalYearKey: string;
  /** 画面の列。行内のどの入力欄かを一意に決める */
  readonly field: YearRowField | null;
  /** 元の列名。`field` が `null` のとき「何が読めなかったか」を伝えるのに要る（§5.3） */
  readonly column: string;
  readonly reason: ImportDiagnostic['reason'];
  /** 値が使われたか。表示文言を変える唯一の分岐 */
  readonly valueKept: boolean;
  /** 元の値。**整形しない**（§5.2） */
  readonly raw: string;
}

type YearRowField =
  'epsYen' | 'roePercent' | 'revenueYen' | 'operatingMarginPercent' | 'dividendYen';
```

**`field` が `null` になる場合がある。** 行そのものが落ちた診断
（`year-out-of-range` / `duplicate-year` / `unknown-note` は `column` が `年度` か `備考`）や、
画面に列が無い項目（`財務` ブロックの `BPS`、`業績` ブロックの `営業利益`）は
セルに紐づかない。**紐づかないものを黙って捨てない。** 行外の警告として別に出す（§5.3）。

#### 列名 → 画面の入力欄

| ブロック | 列              | `field`       | 備考                                   |
| :------- | :-------------- | :------------ | :------------------------------------- |
| 業績     | `EPS`           | `epsYen`      |                                        |
| 業績     | `ROE`           | `roePercent`  |                                        |
| 業績     | `売上高`        | `revenueYen`  |                                        |
| 業績     | `営業利益`      | `null`        | 画面には営業利益**率**しか無い。行外へ |
| 配当     | `一株配当`      | `dividendYen` |                                        |
| 財務     | `BPS`           | `null`        | 画面に欄が無い。PBR の算出元。行外へ   |
| （任意） | `年度` / `備考` | `null`        | 行が落ちた。行外へ                     |

営業利益の診断が `null` になるのは、営業利益率が派生値
（`deriveOperatingMarginPercent()`）で、元の営業利益が読めなければ率も `null` になるため。
**「営業利益率が空欄なのは、元の営業利益が読めなかったからだ」と人に伝わる必要がある**
ので、行外に落として文言で説明する。率の欄そのものを警告表示にしてもよいが、
その欄をユーザーが直接編集できる（＝率を手入力できる）ため、
「読めなかったのは率ではなく営業利益」と区別して伝える。

#### `reason` → `valueKept`

`CompanyForm.tsx:82` の `DISCARDED_REASONS` をドメイン側へ移し、
**列挙の網羅を型で守る**（`reason` に追加したらコンパイルが落ちるように `switch` で書く）。

| `reason`            | `valueKept`   | 人が判断すること                                |
| :------------------ | :------------ | :---------------------------------------------- |
| `suspicious-jump`   | ✅ 採用       | 株式分割の反映漏れか、記念配当か、本当の急変か  |
| `rounded`           | ✅ 採用       | 小数第3位以下を落として問題ないか（通常は無害） |
| `unparsable-value`  | ❌ 空欄       | 空欄のまま進めるか、原典を見て手入力するか      |
| `unsafe-integer`    | ❌ 空欄       | 同上（銭化で桁が溢れた。§8-2）                  |
| `year-out-of-range` | ❌ 行が落ちた | その年度が必要か                                |
| `duplicate-year`    | ❌ 行が落ちた | どちらの値が正しいか（両方落としてある）        |
| `unknown-note`      | ❌ 行が落ちた | 予想か実績か                                    |

### 3.3. 指標単位の不足

```ts
interface MetricGap {
  /** 指標番号。'①'〜'⑩' */
  readonly metric: MetricKey;
  readonly kind: MetricGapKind;
  /** 必要年数（`kind` が年数系のときだけ意味を持つ） */
  readonly requiredYears: number | null;
  /** 実際に埋まっている年数 */
  readonly availableYears: number | null;
}

type MetricGapKind =
  /** ①⑦: 端点（直近・5年前）のどちらかが欠けている。間の年度は欠けていてよい */
  | 'endpoint-missing'
  /** ④⑤⑧: 直近 N 年が連続で全部埋まっていない（`takeCompleteYears`） */
  | 'window-incomplete'
  /** ③: 予想行が無い、または予想EPS・予想配当が欠けている */
  | 'forecast-missing'
  /** ⑥⑨⑩: 取り込み対象外の手入力（株価・貸借対照表）が未入力 */
  | 'manual-input-missing'
  /** ②: 計算はできるが、履歴が短くて上位の区分に到達できない */
  | 'history-shorter-than-top-band';
```

#### 指標別の必要年数

**出典はコードの定数。この表を手で書き換えない**（定数から導出する）。

| 指標               | 必要                               | `kind`                          | 定数                                            |
| :----------------- | :--------------------------------- | :------------------------------ | :---------------------------------------------- |
| ① 増配率           | 配当の直近と**5年前**の2点         | `endpoint-missing`              | `FIVE_YEARS_AGO_INDEX`（`score-company.ts:36`） |
| ② 連続非減配年数   | 10点には**17年**、5点には10年      | `history-shorter-than-top-band` | `CONSECUTIVE_YEARS_BANDS`（`bands.ts:39`）      |
| ③ 予想配当性向     | 予想EPS・予想配当                  | `forecast-missing`              | —                                               |
| ④ EPS CAGR         | EPS **直近6年が連続で全部**        | `window-incomplete`             | `EPS_REQUIRED_YEARS = 6`                        |
| ⑤ ROE平均          | ROE **直近5年が連続で全部**        | `window-incomplete`             | `ROE_AVERAGE_YEARS = 5`                         |
| ⑥ 配当維持可能年数 | 貸借対照表の4項目（手入力）        | `manual-input-missing`          | —                                               |
| ⑦ 売上CAGR         | 売上の直近と**5年前**の2点         | `endpoint-missing`              | `FIVE_YEARS_AGO_INDEX`                          |
| ⑧ 営業利益率       | 営業利益率 **直近5年が連続で全部** | `window-incomplete`             | `OPERATING_MARGIN_YEARS = 5`                    |
| ⑨ MIX係数          | PER・PBR（株価が要る）             | `manual-input-missing`          | —                                               |
| ⑩ 配当利回り       | 株価＋配当                         | `manual-input-missing`          | —                                               |

**①⑦ と ④⑤⑧ を同じ扱いにしない。** ①⑦ は端点2つだけを見るので途中の年度が
欠けていても計算できる（`seriesOf` が年度に揃えた枠を作り、添字がそのまま年数になる）。
④⑤⑧ は `takeCompleteYears` が `null` を1つでも含むと `null` を返すので、
**窓の中が連続で全部埋まっていないと出ない**。「あと1年」の意味が違うため、
画面の文言も分ける。

**② を「不足」と呼ばない。** ② は履歴が3年しかなくても計算でき、
最大3年として採点される（0点や判定不能ではない）。したがって
「データが足りない」ではなく「**17年分ないと10点には到達しない**」と伝える。
ここを他の指標と同じ「不足」表示にすると、実際には出ているスコアを
「出ていない」と誤解させる。

### 3.4. 年度キーの解決

`fiscalYearKey`（`'2026/03'`）の先頭4桁を決算年度にする
（[irbank-json-import.md](./irbank-json-import.md) §3.2 と同じ規則）。

**画面には元のキーも併記する。** 3月期以外の銘柄では `2026/12` が
2026年度になるので、年度だけ出すと原典と突き合わせられない。
決算月が3月以外の実データは未確認（同 §8-3）。

## 4. 誰も検出していない穴

§3 で扱えないもの。**検出できないことを設計書に明記して残す**（黙って通さない）。

| 穴                                     | なぜ検出できないか                                                                                   | 本仕様での扱い                                                                                                                            |
| :------------------------------------- | :--------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------- |
| 銘柄コードの取り違え（実在する別会社） | JSON に**銘柄名が含まれない**（`meta` は `code` / `type` / `item` だけ）。照合対象が無い             | ❌ 検出不能。取り込み後に「銘柄名は取り込めません。コードが正しいか原典で確認してください」と出し、`irbank.net/<code>` へのリンクを添える |
| 単位が桁ごと違う（千円・百万円）       | 4銘柄で全て円の生値と確認済みだが、確認は4銘柄ぶん（同 §2.2）                                        | ⚠️ 部分的。前年比の急変として現れれば `suspicious-jump` に掛かるが、**全年度が一様に1000倍なら掛からない**                                |
| 株価だけが古い                         | `fetchedAt` は**保存した時刻**（`app.ts:80` の `now()`）で、株価を観測した時刻ではない。株価は手入力 | ⚠️ §8-3                                                                                                                                   |
| 複数年にまたがった株式分割             | 1年差の比較なので比率が薄まる（`parse-fy-data.ts:444` のコメントに既知として記載済み）               | ⚠️ 既知の限界。§8-4                                                                                                                       |

## 5. 画面（`CompanyForm.tsx`）

### 5.1. 修正UIは新規に作らない

年度別データの表は**全セルが既に `<input>`** である（`CompanyForm.tsx:520-583`）。
「どうやって修正させるか」に新しい仕組みは要らない。**必要なのは修正すべき場所を
指すことだけ**で、修正手段は既にある。

### 5.2. セル警告の表示

- 該当セルに `aria-invalid="true"` を付ける
- **記号（⚠）と文言を必ず添える。色だけで表現しない**（`.claude/rules/frontend.md`）
- セル直下または行の下に理由を出す。`reason` ごとに固定文言を持つ
- `raw` は**等幅で、そのまま出す**。金額として3桁区切り＋「円」を付けて整形しない。
  整形すると「アプリが算出した金額」に見えるが、これは**読めなかった元の値**である。
  `.claude/rules/frontend.md`「裸の数字を出さない」は算出値の表示規則であり、
  原典の生値の提示には当てはまらない
- `suspicious-jump` の `raw` は `"1234 -> 2900"`（銭）の形。**文字列を再パースして
  円に整形しない**（区切り文字の形式に画面が依存すると壊れる）。
  構造化して渡す案は §8-5

### 5.3. 行に紐づかない警告

`field` が `null` の警告（§3.2）は、表の外・表の直前にまとめて出す。
「◯年度の行は取り込めませんでした（理由）。必要なら手入力してください」の形。
**件数だけに潰さない。年度と理由を1件ずつ出す。**

### 5.4. 指標の不足表示

表の下に、埋まっていない指標を1行ずつ出す。文言は `kind` で分ける。

| `kind`                          | 文言の型                                                                                |
| :------------------------------ | :-------------------------------------------------------------------------------------- |
| `endpoint-missing`              | 「① 増配率: 2021年度の1株配当が必要です（5年前の値）」                                  |
| `window-incomplete`             | 「④ EPS CAGR: 直近6年が連続で必要です（現在4年）。2020・2021年度のEPSが空欄です」       |
| `forecast-missing`              | 「③ 予想配当性向: 予想行が取り込めませんでした。予想EPSと予想配当を手入力してください」 |
| `manual-input-missing`          | 「⑩ 配当利回り: 現在株価を入力してください」                                            |
| `history-shorter-than-top-band` | 「② 連続非減配年数: 現在4年分で採点しています。10点には17年分の履歴が必要です」         |

**「あと何年」ではなく「どの年度が空欄か」を出す。** ④ は連続窓なので、
年数だけ言われても人はどこを埋めればいいか分からない。

### 5.5. 取り込みのマージ規則（§2.2 の修正）

`buildRowsFromImport(records)` を `mergeRowsWithImport(existingRows, records)` に置き換える。
**取り込みは手入力を破壊しない。**

1. **取り込みが値を持つ（非 `null`）セル** → 取り込み値で上書きする
2. **取り込みが `null` のセル** → **既存の手入力を残す**（空欄で潰さない）
3. **取り込みに無い年度の行** → そのまま残す（削除しない）
4. **取り込みにあって既存に無い年度** → 行を追加する
5. 並びは「予想行 → 実績年度の降順」。同じ年度の行を2つ作らない
6. 上書きが発生したら件数を通知する（「3件の入力値を取り込み値で置き換えました」）

規則2が要点である。取り込みは①②④⑦ の古い年度を埋められないのだから、
「取り込みに無い」を「空である」と解釈してはいけない。

### 5.6. 保存前の確認

`valueKept: true` の警告（`suspicious-jump` / `rounded`）が残ったまま
「解析して保存」を押したとき、**確認を1回挟む**。

- 「前年比が±80%を超えた値が2件あります。値を確認しましたか？」
- 「確認した」を押すと保存へ進む。「戻る」で表の該当セルへスクロールする

**編集したセルの警告は消す。** ユーザーが値を直した時点でその警告は用済みになる。
再検証はしない（手入力値の妥当性は取り込みの責務ではない）。

⚠️ **「確認した」という判断を DB に残すかは未決**（§8-6）。
残さない場合、一覧画面では「人が確認した値」と「確認していない値」が区別できない。

## 6. 例外・境界条件

| 状況                                 | 挙動                                                                                        |
| :----------------------------------- | :------------------------------------------------------------------------------------------ |
| `diagnostics` が空                   | 警告表示なし。通知も出さない（今と同じ）                                                    |
| 診断が同じ年度・同じ列に複数         | すべて出す。1件に潰さない（`rounded` と `suspicious-jump` は同時に起こりうる）              |
| `fiscalYearKey` が年度に解決できない | `year-out-of-range` として既に記録済み。`fiscalYear` は解決せず、キー文字列のまま行外に出す |
| 診断の年度が表のどの行にも無い       | 行外の警告として出す（行が落ちた場合。§5.3）                                                |
| 取り込みが 0 件（`no-usable-year`）  | 取り込み自体が失敗する（`Result` の `err`）。この設計書の対象外                             |
| すべての指標が埋まっている           | 不足表示なし                                                                                |
| 実績が1年もない                      | `seriesOf` が空配列を返す。①②④⑤⑦⑧ すべてを不足として出す                                    |
| 配当が全年度 0（無配）               | **不足ではない。** 0 は値であり、①は0点、②は0年として採点される。不足に出さない             |
| 株価が 0                             | **不足ではない。** ⑩ は `price-zero` で判定不能を返す。指標側の責務であり、ここでは扱わない |

**「値が 0」を「不足」に出してはいけない。** 無配とデータ欠損の区別は
このプロジェクトの根幹（`CLAUDE.md`）で、不足表示がここを混同すると、
無配銘柄に「データを入力してください」と出し続けることになる。

### 7.3. マージ（`mergeRowsWithImport`）

- [x] 既存に 2019年度（EPS `100`）があり取り込みに 2019 が無い → **2019行が EPS `100` のまま残る**（§2.2 の回帰テスト）
- [x] 既存の 2019 に EPS `100`、取り込みの 2019 は EPS `null` / 売上高 `500` → EPS `100` が残り、売上高に `500` が入る
- [x] 既存の 2019 に EPS `100`、取り込みの 2019 に EPS `120` → `120` で上書きし、上書き件数 1 を返す
- [x] 「年度を追加」で足した 2018行（手入力あり）→ 取り込み後も残る
- [x] 戻り値に同じ年度の行が2つ現れない
- [x] 先頭が予想行、以降は実績年度の降順
- [x] 取り込みを**2回連続**で実行 → 1回目と同じ結果になる（冪等）
- [x] 既存行が空、取り込みが6年ぶん → 6年ぶんが入り、上書き件数 0

行の同一性は**年度だけ**で決めた（規則5「同じ年度の行を2つ作らない」を満たすため）。
その帰結として、予想年度が実績として取り込まれた場合は行を増やさずその行を実績に変える
（旧 `buildRowsFromImport` は値ごと捨てていた）。

### 7.4. 画面

- [x] `suspicious-jump` の該当セルに `aria-invalid="true"` が付く
- [x] 警告に⚠記号と文言が付く（色クラスだけになっていない）
- [x] セルを編集すると `aria-invalid` が外れる
- [x] `field: null` の警告が表の外に、年度と理由付きで1件ずつ出る（件数に潰れない）
- [x] `valueKept: true` の警告が残った状態で送信 → 確認が1回入る
- [x] 確認を経て送信すると、従来と同じ `AnalyzeCompanyRequest` が飛ぶ（ペイロードは変えない）
- [x] 診断が0件なら確認は入らない
- [x] 確認バナー表示中にセルを直してから「確認した」を押すと、**直した値**が飛ぶ

上の4件は、レンダリング結果ではなく**表示を決める純粋関数**（`warningsForCell` /
`cellWarningText` / `dropEditedWarnings` / `rowlessWarnings`）で検証している。
`@testing-library/react` は未導入で、DOM を組み立てるテストが書けないため
（`tests/frontend/company-form.test.tsx` の先頭コメント）。導入するかは別途。

保存前の確認（§5.6）も同じ理由で、送信の可否を決める `hasUnconfirmedWarnings` /
`shouldShowConfirmation` と文言の `confirmWarningsText` で検証している。
**「戻る」でセルへスクロールする挙動は実装していない**（スクロール位置を検証できず、
確認をキャンセルして送信しないところまでで受入基準を満たす）。

最後の1件（確認中の編集）は DOM を介さないと再現できないため、テストではなく**設計で
保証している**。確認待ちの state は `boolean` だけで、ペイロードは「確認した」を押した
瞬間に `handleSubmit` が最新の state から組み立て直す。スナップショットを保持しない
（当初の実装は保持しており、直した値が捨てられていた。code-reviewer 指摘、2026-07-30）。
文言は `rounded` も対象に含むため「前年比が±80%」に限定していない。

確認待ちの `boolean` は、**警告の中身が入れ替わる操作（再取り込み）でも解除する**
（`handleImport` が確認待ちをリセットする。同 code-reviewer 指摘）。解除しないと、
1回目の警告に対して確認を済ませたあと同じ銘柄コードで取り込み直した2回目の警告に対して
確認が1回も入らずに素通りしてしまう。

## 8. 未決事項

1. 🔴 **frontend → domain の実行時 import の範囲。**
   §3.3 の充足判定は入力のたびに再計算するので、frontend から
   `src/domain/scoring/coverage.ts` を実行時 import したい。
   [ADR-0008](../../adr/0008-frontend-domain-runtime-import.md) は現在
   `deriveMarketMultiples()` に限定しており、`src/domain/scoring/` を明示的に対象外にしている。

   - **推奨**: ADR-0008 を改訂し、`coverage.ts`（純粋・区分表を含まない・判定を返さない）を
     対象に加える。`bands.ts` と採点関数は対象外のまま
   - 代案: 充足判定も取り込み時点のみサーバーで計算する。ADR は触らずに済むが、
     手入力で埋めても表示が更新されないので §5.4 の価値が大きく下がる

2. 🟡 **`unsafe-integer` の扱いは §8-2 の再掲。**
   メガバンクの総資産は銭化で `MAX_SAFE_INTEGER` を超え、手入力でも拒否される
   （[irbank-json-import.md](./irbank-json-import.md) §8-1）。
   この設計書は「読めなかったことを人に伝える」までで、**通せるようにはしない**。
   `BigInt` か円単位かの決定が別途必要。

3. 🟡 **株価の観測時刻を持つか。**
   `fetchedAt` は保存時刻であって株価を見た時刻ではない。⑨⑩ は株価に依存するので、
   「10日前の株価で算出したPER」を今の値として表示しうる。
   `CLAUDE.md`「取得した株価・配当データは必ず取得時刻とセットで保存する」に照らすと
   不足。スキーマ変更を伴うので本仕様の対象外。

4. 🟢 **複数年にまたがった株式分割は検知できない。**
   1年差の比較なので比率が薄まる（`parse-fy-data.ts:444` に既知として記載済み）。
   T-035 の範囲。本仕様では変えない。

   > 📌 **2026-07-30 追記。解消の道筋ができた。**
   > [market-data-source.md](./market-data-source.md) で株式分割イベント（日付＋比率）が
   > 実データで取れることを確認した。急変した年度と分割日を突き合わせれば、
   > 「分割か本物の急変か機械的に区別できない」という本仕様の前提そのものが変わり、
   > **「これは分割です」と断定できる**ようになる。同設計書 §8-4。

5. 🟢 **`ImportDiagnostic` を判別可能ユニオンにするか。**
   `reason` ごとに持つべき情報が違う（`suspicious-jump` は前後の値と変化率、
   `duplicate-year` は年度キーだけ）。今は全部 `raw: string` に押し込んでいるため、
   §5.2 のとおり画面が文字列を再パースしないと前後の値を出せない。
   ADR-0003 で `MetricScore` を判別可能ユニオンにしたのと同じ筋。
   影響が `financial-source.ts` / `parse-fy-data.ts` / DTO / 画面 / テストに及ぶので、
   §7 を満たしたあとに別途。**本仕様では `raw` をそのまま出す**（§5.2）。

6. 🟡 **「人が確認した」を DB に残すか。**
   残さないと、一覧画面で確認済みの値と未確認の値が区別できない。
   残すなら `companies` にスキーマ追加が必要。**本仕様は画面で見せるところまでとし、
   保存は次段**。ここを決めずに §5.6 を実装しても手戻りはしない（確認の UI は共通）。
