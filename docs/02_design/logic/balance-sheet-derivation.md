# 貸借対照表項目の導出 仕様書（⑥ の入力・IRバンク由来）

> **依存する指標:** [dividend-sustainability-scoring.md](./dividend-sustainability-scoring.md)（指標⑥）
> **依存する取り込み:** [irbank-json-import.md](./irbank-json-import.md)（データ源・値の型の揺れ・銭化）
> **関連機能:** [F-07 / F-19](../../01_requirements/features.md)
> ステータス: 🔴 未実装（本書は Step1 の設計）

## 1. 概要

指標⑥（配当維持可能年数）が要求する貸借対照表の4項目のうち、
**IRバンクの `fy-data-all.json` から導出できる2項目**を自動で埋める。

| 項目                 | `BalanceSheetSnapshot` の欄 | 本書の範囲                                |
| :------------------- | :-------------------------- | :---------------------------------------- |
| 流動資産             | `currentAssetsSen`          | ❌ **対象外**（手入力のまま）             |
| 投資有価証券         | `investmentSecuritiesSen`   | ❌ **対象外**（手入力のまま）             |
| **負債総額**         | `totalLiabilitiesSen`       | ✅ 総資産 − 純資産から算出                |
| **前期末の配当総額** | `previousDividendTotalSen`  | ✅ 配当ブロックの列を読む（負値検査つき） |

⑥ は4項目すべてが揃わないと判定できないため、**本書だけでは ⑥ は埋まらない。**
本書の効果は**手入力を4項目から2項目へ減らすこと**に限られる。

> **なぜ2項目だけなのか。** 2026-08-05 に実測した結果、流動資産と投資有価証券は
> IRバンクの JSON にも HTML にも**投資有価証券が存在しない**（§7.3）。
> この2項目を自動化するには EDINET の XBRL が要り、本書とは別の取得経路になる。

### 1.1. 本書は「計算」だけを定める

`.claude/skills/new-logic-spec` の手順に従い、**純粋関数として定義する。**
DB にも HTTP にも触らない。取得は [irbank-json-import.md](./irbank-json-import.md) §4 が正。

⚠️ 同スキルは出力先を `src/lib/` と書いているが、`src/lib/` は移行ブリッジで
**新しいコードを書かない**（ルート `CLAUDE.md`）。本書の実装先は `src/domain/company/` とする。
[irbank-json-import.md §3.5](./irbank-json-import.md) が「算出はすべて `src/domain/company/` の
純粋関数が担う」と定めており、`operating-margin.ts` / `market-multiples.ts` と同じ場所に揃える。

## 2. 入出力

### 2.1. 負債総額の算出

**入力**

| 項目             | 型               | 単位           | 備考                         |
| :--------------- | :--------------- | :------------- | :--------------------------- |
| `totalAssetsYen` | `number \| null` | **円**（整数） | 財務ブロック「総資産」の生値 |
| `netAssetsYen`   | `number \| null` | **円**（整数） | 財務ブロック「純資産」の生値 |

**出力**

`number | null` を返さない。**なぜ算出できなかったかを判別可能ユニオンで返す。**

```ts
export type TotalLiabilitiesDerivation =
  /** 算出できた。`valueSen` は銭（整数）。**0 もここに入る**（無借金。§5.4） */
  | { readonly kind: 'derived'; readonly valueSen: number }
  /** 総資産・純資産のいずれかが `null`。正常な欠損（§5.1） */
  | { readonly kind: 'input-missing' }
  /** 円の生値が整数でなかった。データ不良（§5.1） */
  | { readonly kind: 'not-integer' }
  /** 総資産 < 純資産。会計恒等式に反する（§5.3） */
  | { readonly kind: 'negative-liabilities' }
  /** 差を銭にすると安全整数を超える（§3.2） */
  | { readonly kind: 'unsafe-integer' };

export function deriveTotalLiabilities(
  totalAssetsYen: number | null,
  netAssetsYen: number | null,
): TotalLiabilitiesDerivation;
```

> **なぜ `null` を返さないか。** §5.1 は失敗のうち一部で診断（`ImportDiagnostic`）を
> 残すことを要求するが、**診断には `block` / `fiscalYearKey` / `column` が要り、
> 純粋関数はそれを知らない。** `null` だけ返すと、呼び出し側（infra）は
> 「正常な欠損」と「会計恒等式違反」を区別できず、§5.1 の表を実装できない。
> 判別可能ユニオンで理由を返し、**診断の組み立ては infra が行う**。
> `MetricScore` の `unavailableReason`（[ADR-0003](../../adr/0003-metric-score-discriminated-union.md)）と同じ形である。

`kind` から診断への対応は §5.1 の表が正。

> ⚠️ **この関数だけ入力が円である。** プロジェクト規約（`CLAUDE.md`）の
> 「金額は銭単位の整数」に対する**意図的な例外**で、理由は §3.2 にある。
> 引数名に `Yen` を付けて取り違えを防ぐ。**`valueSen` は銭**なので、
> 呼び出し側から見た出力は他の導出関数（`deriveOperatingMarginPercent` 等）と揃う。

### 2.2. 前期末の配当総額の読み取り

配当ブロックの「剰余金の配当」列（**円**の生値）を銭へ変換して読む。**2段階ある。**

| 項目 | 型               | 単位           | 備考                            |
| :--- | :--------------- | :------------- | :------------------------------ |
| 入力 | 列の生値         | **円**         | `number` / 数値文字列 / `"-"`   |
| 出力 | `number \| null` | **銭**（整数） | `"-"` は `null`。**0 とは別物** |

1. 既存の `senAt()`（`src/infra/irbank/parse-fy-data.ts:177`）で銭へ変換する
2. **結果が負なら `null` に上書きし、`inconsistent-value` の診断を1件残す**（§5.5）

> 🔴 **`senAt()` を「負なら `null`」に変えてはいけない。**
> `senAt()` は業績・財務・配当の**全金額列で共有**されており、営業利益は
> 営業赤字で正当に負を取る。既存テスト
> `tests/infra/irbank/parse-fy-data.test.ts:316`（`負の値も銭になる`）が
> この挙動を固定しており、共有関数を変えるとそれを壊す。
> したがって**負の検査は「剰余金の配当」列にだけ被せる**。
> 実装は `senAt()` を包む専用の読み取り関数にする（§9）。

**「計算は無い」わけではない。** 上の2段目は既存の読み取り経路に無い新しい判定である。

### 2.2.1. 負債総額の診断も infra が組み立てる

`deriveTotalLiabilities()` は理由だけを返す（§2.1）。`ImportDiagnostic` の
`block` / `fiscalYearKey` / `column` を埋めて `diagnostics` へ積むのは
`parse-fy-data.ts` の責務である。`block` は `'財務'`、`column` は `'総資産'` と `'純資産'` の
うち**先に読んだ `'総資産'`** を使う（2列から1つの値を作るため、どちらか一方に寄せる。
`raw` には `"<総資産> - <純資産>"` の形で両方を残し、原因調査で追える状態にする）。

### 2.3. 対象年度の選択

両項目とも、`BalanceSheetSnapshot` が**年度を持たない**（`company.ts:33`）ため、
どの決算年度の値を採るかを決める必要がある。

> **各ブロックの実績行を決算年度の降順に走査し、その列が読めた最初の年度を採る。**

- **実績行のみ**を対象とする（`isForecast === true` は飛ばす）
- 読めない年度（`"-"`・数値として読めない・銭化で桁あふれ）は飛ばして次の年度へ進む
- 1件も読めなければ `null`

**負債総額は2列（総資産・純資産）を使うので、年度の確定条件を明示する。**

> **両方が読めて、かつ算出まで成功した最初の年度を採る。**
> 片方だけ読めた年度・算出に失敗した年度は**その年度ごと飛ばして次の年度へ進む。**

最新年度で総資産だけ読めて純資産が `"-"` の場合、`fiscalYear` をその年度のまま
返して値だけ `null` にはしない。**値と年度は必ず対で確定する**（片方だけ埋まった
状態を作ると、画面が「2026年3月期・データなし」という無意味な組を表示する）。

診断は「飛ばした年度ごと」に残る。最新年度が桁あふれで1つ前が読めた銘柄では、
`unsafe-integer` が1件出たうえで**値は算出される**（診断が出た＝値が無い、ではない）。

走査そのものは既存の `latestActualBpsSen`（`parse-fy-data.ts:540-551`）と**同じ規則**で、
新しい規則を持ち込まない。BPS は1列なので「両方読めた年度」の条件だけが本書の追加分である。

**採用した決算年度を値と一緒に返す。** ⑥ の入力は年度を持たないので、
そうしないと「3年前の負債総額」と「今期の配当総額」を混ぜたことに誰も気づけない。

```ts
/** 取り込みで得た金額と、それがどの決算年度の値かの組 */
export interface ImportedAmount {
  /** 銭（整数） */
  readonly valueSen: number;
  /** 決算年度。2026年3月期なら 2026 */
  readonly fiscalYear: number;
}
```

`ImportedFinancials`（`src/domain/company/financial-source.ts:63`）に2欄を追加する。

```ts
  /** ⑥ 用。財務ブロックの最新実績年度から算出した負債総額。算出できなければ `null` */
  readonly totalLiabilities: ImportedAmount | null;
  /** ⑥ 用。配当ブロックの最新実績年度の配当総額。読めなければ `null` */
  readonly previousDividendTotal: ImportedAmount | null;
```

> **2欄の決算年度が食い違っても取り込みは止めない。** 診断も出さない。
> この取り込みは保存せずフォームの初期値を返すだけ（[irbank-json-import.md §1](./irbank-json-import.md)）で、
> **確定は人が行う**ため。年度を画面に出して人が判断する（[import-review.md](./import-review.md) と同じ方針）。
> 実測では 7203 が業績 2023〜2027 / 財務 2022〜2026 と1年ずれており、
> ブロック間の年度ずれは例外ではなく常態である。

## 3. 計算式

### 3.1. 負債総額

$$\text{負債総額} = \text{総資産} - \text{純資産}$$

会計恒等式（資産 = 負債 + 純資産）そのものである。IRバンクの財務ブロックには
負債の列が無いが、総資産と純資産は全銘柄・全年度で取れる（§7.1）。

### 3.2. 減算は円で行い、その結果を銭へ変換する

**総資産・純資産を個別に銭化してから引いてはいけない。**

`Number.MAX_SAFE_INTEGER` は 9,007,199,254,740,991（≈9.007e15）で、
銭化すると約90兆円が上限になる（[irbank-json-import.md §3.4](./irbank-json-import.md)）。
実測値で両者を比較する。

| 銘柄 | 総資産（円） | 銭化                    | 純資産（円） | 負債総額（円） | 銭化       |
| :--- | -----------: | :---------------------- | -----------: | -------------: | :--------- |
| 7203 |      105.5兆 | 1.06e16 ❌ **桁あふれ** |       41.0兆 |         64.5兆 | 6.45e15 ✅ |
| 8306 |      431.7兆 | 4.32e16 ❌              |       23.7兆 |        408.0兆 | 4.08e16 ❌ |
| 9433 |       19.1兆 | 1.91e15 ✅              |        5.6兆 |         13.5兆 | 1.35e15 ✅ |
| 1301 |      2,141億 | 2.14e13 ✅              |        789億 |        1,353億 | 1.35e13 ✅ |

**7203（トヨタ）が分岐点である。** 総資産を先に銭化すると桁あふれで
`kind: 'unsafe-integer'` に倒れるが、円で引いてから銭化すれば安全整数に収まる。
**先に引く**だけで1銘柄が救われる。

円の生値は整数で、桁は最大でも約4.3e14（8306 の総資産）である。
`Number.MAX_SAFE_INTEGER`（9.007e15）に対して20倍以上の余裕があり、
**円のままの減算は浮動小数点誤差を持たない**（IEEE 754 の double は
2^53 未満の整数を厳密に表現する）。したがって `parseFloat` を経由しない
という規約（`.claude/rules/backend.md`）にも抵触しない。

> 8306 は円で引いても銭化で超える。**銀行は本書の範囲では埋まらない。**
> ただし §7.2 のとおり、銀行では ⑥ という指標自体が定義できないため実害は無い。

### 3.3. 前期末の配当総額

**四則演算は無い。** IRバンクの配当ブロック「剰余金の配当」（円の生値）を
銭化するだけである（負値の検査は §2.2 の2段目にある）。

実測した桁は 9.7億円（1301 の 2023/03）〜 8,489億円（8306 の 2026/03）で、
銭化しても 8.49e13 と安全整数に十分収まる。**この列で桁あふれは起きない。**

## 5. 例外処理

### 5.1. 負債総額

| 状況                                           | `kind`                     | 診断（infra が組み立てる） | 理由                                   |
| :--------------------------------------------- | :------------------------- | :------------------------- | :------------------------------------- |
| 総資産・純資産のいずれかが `null`              | `input-missing`            | **出さない**               | 正常な欠損。0 ではない                 |
| **純資産が負（債務超過）**                     | `derived`                  | 出さない                   | §5.2                                   |
| **総資産 − 純資産 が負**                       | `negative-liabilities`     | **`inconsistent-value`**   | 会計恒等式に反する。データ不良（§5.3） |
| **総資産 − 純資産 が 0**                       | `derived`（`valueSen: 0`） | 出さない                   | 無借金。`null` ではない（§5.4）        |
| 入力が整数でない                               | `not-integer`              | `unparsable-value`         | 円の生値は整数のはず。実測でも全て整数 |
| 差の銭化が `Number.isSafeInteger` を満たさない | `unsafe-integer`           | `unsafe-integer`           | 8306 が該当。既存 `senAt()` と同じ扱い |

> 🆕 **`inconsistent-value` は新設する診断種別である。**
> 既存の `ImportDiagnostic.reason`（`financial-source.ts:34-51`）には
> 「値は数値として読めたが、他の値と突き合わせると成立しない」を表す種別が無い。
> `unparsable-value`（「数値として読めない値だった」）を流用すると、
> 原因調査で「本当に読めなかったのか」「恒等式違反なのか」を診断ログから
> 区別できなくなる。診断は原因調査のために残すもの（`.claude/rules/backend.md`）なので、
> 意味の合わない種別を流用しない。波及範囲は §9 に挙げた2箇所に限られる。

### 5.2. 純資産が負でも算出する

債務超過企業は純資産が負になる。このとき

$$\text{負債総額} = \text{総資産} - (-|\text{純資産}|) = \text{総資産} + |\text{純資産}|$$

となり、**総資産より大きい負債総額が正しく出る。** これは異常値ではなく実態である。
`null` に倒すと、⑥ が「債務超過 → 0点」（[§0.3](../../01_requirements/scoring-requirements.md)）を
出せなくなり、**最も危険な銘柄が判定不能で見えなくなる。**

### 5.3. 差が負のときだけデータ不良とみなす

負債総額が負になるのは会計上ありえない（負債は 0 以上）。総資産と純資産の
どちらかが誤っているが、**どちらが誤りか機械的に決められない**ので値を採らない。
`deriveTotalLiabilities()` は `{ kind: 'negative-liabilities' }` を返し、
infra がそれを `inconsistent-value` の診断に変換して残す（§2.2.1）
（`.claude/rules/backend.md` 「検証に落ちたデータは捨てずに記録する」）。
その年度は飛ばして次の年度へ進む（§2.3）。

### 5.4. 差が 0 は `null` ではなく 0

無借金企業（負債総額 0）は実在する。0 を `null` にすると ⑥ の
ネットキャッシュが判定不能になる。**`null`（判定不能）と 0 は別物**（`CLAUDE.md`）。

### 5.5. 前期末の配当総額

| 状況                     | 戻り値 | 診断                     | 理由                                                                             |
| :----------------------- | :----- | :----------------------- | :------------------------------------------------------------------------------- |
| `"-"`（無配当・非開示）  | `null` | 出さない                 | 正常な欠損。**0 ではない**                                                       |
| **全年度が `"-"`**       | `null` | 出さない                 | 7203 が該当（§7.1）。IFRS 採用企業では列が埋まらない                             |
| **0（無配）**            | **0**  | 出さない                 | ⑥ 側がゼロ除算として `null` に倒す（⑥ §5）。ここでは 0 のまま                    |
| 数値として読めない文字列 | `null` | `unparsable-value`       | 既存 `senAt()` の挙動をそのまま使う                                              |
| 銭化で安全整数を超える   | `null` | `unsafe-integer`         | 既存 `senAt()` の挙動をそのまま使う。実測では起きない（§3.3）                    |
| **負の値**               | `null` | **`inconsistent-value`** | 配当総額が負は制度上ありえない。データ不良。**`senAt()` の外で判定する**（§2.2） |

> **0 をここで `null` に丸めない。** 無配（0円）とデータ欠損は
> データ層で区別し続ける（`CLAUDE.md`）。ゼロ除算の判断は ⑥ の責務。

### 6.1 境界値ちょうど

**負債総額（`deriveTotalLiabilities`。純粋関数の単体テスト）**

- [ ] 総資産 `1000` 円 / 純資産 `1000` 円 → `{ kind: 'derived', valueSen: 0 }`
      （`input-missing` でも `negative-liabilities` でもない）
- [ ] 総資産 `1000` 円 / 純資産 `1001` 円 → `{ kind: 'negative-liabilities' }`
- [ ] 差が `90,071,992,547,409` 円（銭化で `9,007,199,254,740,900`）→ `derived`
- [ ] 差が `90,071,992,547,410` 円（銭化で `9,007,199,254,741,000` > `MAX_SAFE_INTEGER`）
      → `{ kind: 'unsafe-integer' }`
- [ ] 総資産 `105,522,331,000,000` / 純資産 `41,020,068,000,000`（7203 の実測値）
      → `valueSen: 6,450,226,300,000,000`
      （**総資産を先に銭化していたら `unsafe-integer` になる回帰テスト**）
- [ ] 総資産 `1000.5` 円 → `{ kind: 'not-integer' }`

**対象年度の選択 — 負債総額（財務ブロック）**

- [ ] 最新実績年度で両方読めれば、その年度を `fiscalYear` に載せる
- [ ] 最新実績年度が読めず1つ前の年度が読める → **1つ前の年度を採り、その年度を載せる**
- [ ] **最新実績年度は総資産だけ読めて純資産が `"-"`、1つ前は両方読める**
      → **1つ前の年度を採る**（最新年度で `fiscalYear` だけ確定させない。§2.3）
- [ ] **逆方向も踏む**: 最新実績年度は純資産だけ読めて総資産が `"-"`、1つ前は両方読める
      → **1つ前の年度を採る**（2列のどちらが欠けても同じ挙動）
- [ ] 最新実績年度が `unsafe-integer` で1つ前が算出できる
      → **1つ前の年度の値を返し、かつ `unsafe-integer` の診断が1件残る**
- [ ] 最新実績年度が `negative-liabilities`（総資産 < 純資産）で1つ前が算出できる
      → **1つ前の年度の値を返し、かつ `inconsistent-value` の診断が1件残る**
- [ ] 実績行が1件も無い（予想行だけ）→ `null`
- [ ] 予想行に値があっても**採らない**（実績行のみ走査する）

**対象年度の選択 — 前期末の配当総額（配当ブロック）**

財務ブロックと**同じ規則**を配当ブロックにも課す（§2.3）。片方だけテストしない。

- [ ] 最新実績年度で読めれば、その年度を `fiscalYear` に載せる
- [ ] 最新実績年度が `"-"` で1つ前の年度が読める → **1つ前の年度を採り、その年度を載せる**
- [ ] 実績行が1件も無い（予想行だけ）→ `null`
- [ ] 予想行に値があっても**採らない**（実測では予想行は常に `"-"`。§7.1）
- [ ] 負債総額と配当総額で `fiscalYear` が食い違っても、**両方とも返す**
      （取り込みを止めない。診断も出さない。§2.3）

### 6.2 負の値

- [ ] 総資産 `1000` 円 / 純資産 `-500` 円（債務超過）
      → `{ kind: 'derived', valueSen: 150000 }`（`negative-liabilities` に倒さない）
- [ ] 剰余金の配当が `-1` 円 → **`null`** ＋ **`inconsistent-value`** を1件
- [ ] 上記で **`senAt()` 自体は `-100` 銭を返している**こと（負の検査は外側にある。§2.2）
- [ ] 総資産が負 かつ 純資産が負 で差が正 → `derived`（総資産の符号だけでは弾かない）
- [ ] **既存テスト `負の値も銭になる`（`parse-fy-data.test.ts:316`）が引き続き通る**
      （営業利益の負値を壊していないことの回帰確認）

### 6.3 無配・0

## 7. 実データによる検証（2026-08-05 実施）

推測ではなく、フィクスチャ4銘柄と実際の HTTP 応答で確認した結果に基づく。

### 7.1. 「剰余金の配当」は実在するが、IFRS 採用企業では空

[irbank-json-import.md §2.3](./irbank-json-import.md) は
「`balanceSheet` に対応する列はこの JSON に無い」と書いているが、
**配当総額に関してはこの記述が誤りである。** 配当ブロックの `meta.item.年度` は

```
["一株配当", "剰余金の配当", "自社株買い", "配当性向", "総還元性向", "純資産配当率"]
```

で、「剰余金の配当」が配当総額（円）にあたる。同 §2.3 の「使う列」から漏れていただけである。

| 銘柄 | 2023/03 | 2024/03 | 2025/03 | 2026/03 | 2027/03（予想） |
| :--- | ------: | ------: | ------: | ------: | :-------------- |
| 9433 | 2,871億 | 2,976億 | 2,869億 | 3,015億 | `"-"`           |
| 8306 | 3,805億 | 4,400億 | 5,332億 | 8,489億 | `"-"`           |
| 1301 |   9.7億 |  10.8億 |  11.9億 |  15.5億 | `"-"`           |
| 7203 |   `"-"` |   `"-"` |   `"-"` |   `"-"` | `"-"`           |

> 億円表示は**四捨五入**（9433/8306 は整数位、1301 は小数第1位）。正は
> `tests/fixtures/irbank/*.json` の生値であり、この表は読みやすさのための換算である。

**予想行は全銘柄で `"-"`。** ⑥ が要求するのは前期末の実績なので支障はない。

**7203 は全年度が `"-"`。** IFRS 採用企業ではこの列が埋まらないとみられる。
§5.5 のとおり `null` に倒し、手入力へ戻す。

値の妥当性も確認した。9433 の 2026/03 は純利益 707,112百万に対し配当総額 301,547百万で
配当性向 42.6%、実際の配当方針と整合する。さらに **2024/03 → 2025/03 で
一株配当は 70円 → 72.5円 と増えているのに総額は 2,976億 → 2,869億に減っている**
（生値では 297,575,000,000 円 → 286,885,000,000 円）。
自社株買いで株数が減った効果で、**「一株配当 × 株数」で代用してはいけない**ことの裏付けになる。

### 7.2. ⑥ は日本基準の事業会社にしか定義できない

流動資産と投資有価証券を探す過程で判明した、本書より上位の制約である。

- **銀行の貸借対照表は流動・固定に分かれない。** 実測で IRバンクの BS ページは
  8306 に「流動資産 1兆9,559億」を表示するが、同社の総資産は 431兆円である。
  この「流動資産」が何を指すのか説明できない
- **IFRS 採用企業に「投資有価証券」という科目は無い**（金融資産の区分が異なる）

したがって ⑥ は、金融業・IFRS 採用企業では XBRL を入れても埋まらない。
**`null`（判定不能）に倒すのが正しい挙動**であり、[§0.5](../../01_requirements/scoring-requirements.md) の
「判定不能は総合点で 0点として合算し、有効指標数を併記する」がそのまま適用される。

§3.2 で 8306 の負債総額が桁あふれで `null` になることは、この意味で**実害が無い**。
桁あふれする規模の銘柄と、⑥ が定義できない銘柄が一致するためである。

### 7.3. 流動資産・投資有価証券を本書の範囲外にした根拠

| 取得元                                          | 流動資産 | 投資有価証券 | 実測                                     |
| :---------------------------------------------- | :------- | :----------- | :--------------------------------------- |
| IRバンク `fy-data-all.json`                     | ❌       | ❌           | 財務ブロックに列が無い                   |
| IRバンク HTML（`irbank.net/{EDINETコード}/bs`） | ⭕       | ❌           | 4銘柄すべてで「投資有価証券」が不在      |
| `f.irbank.net/files/{code}/` の他の JSON        | ❌       | ❌           | `fy-data-all.json` 以外は 302 / 404      |
| EDINET API v2（XBRL）                           | ⭕見込み | ⭕見込み     | **未検証**。Subscription-Key 必須（401） |

投資有価証券は IRバンクのどの経路にも無く、**XBRL 以外に手段が無い。**
流動資産だけを HTML から取っても ⑥ は埋まらないため、
**HTML スクレイピングは採らない**（規約リスクと HTML 変更への脆さに見合わない）。

EDINET の XBRL を採るかは本書の範囲外とし、別途 ADR で決める。判断材料:

- 銘柄コードから docID を直接引けない（`documents.json` は**日付単位**の提出一覧）
- ZIP 解凍が要る。Workers の `DecompressionStream` は gzip / deflate のみで
  ZIP を展開できず、依存追加（`fflate` 等）が必要になる
- タクソノミの揺れ（企業独自の拡張要素、連結/単体・当期/前期のコンテキスト選択）
- EDINETコードリスト（証券コード ↔ EDINETコードの対応表）はキー無しで取得できる
  （実測 200 / 569KB）ので、対応表の入手だけは障害にならない

## 10. 未決事項

**実装をブロックするものは無い。** いずれも本書の前提のまま実装でき、
後から差し替えられる。ただし 10-1 は ⑥ の算出値そのものに効くので、
実装後の値をユーザーが見て違和感があれば最初に疑うべき箇所である。

### 10-1. 🟡 「剰余金の配当」と「前期末の配当総額」は厳密には同じでない

「剰余金の配当」は**当期に支払った**配当（株主資本等変動計算書ベース）で、
3月期なら **前期の期末配当（6月支払）＋ 当期の中間配当（12月支払）**にあたる。
一方 ⑥ の「前期末の配当総額」は、直近の決算で確定した**年間配当**の総額を指す。
**半期ぶんずれる。**

ずれの大きさを実測した（`一株配当 × 概算株数` と比較。株数は `株主資本 ÷ BPS` で概算）。

| 銘柄 | 2023/03 | 2024/03 |    2025/03 |   2026/03 |
| :--- | ------: | ------: | ---------: | --------: |
| 9433 |   −1.4% |   +2.1% |      −0.5% |     −1.0% |
| 1301 |   −1.4% |   +2.0% | **−11.4%** | **+6.8%** |

配当が横ばいの年は ±2% 以内に収まるが、**増配・減配の年に開く**（1301 の 2025/03 は
−11.4%）。この比較自体も概算株数を使っているため、ずれの全部が意味の差ではない。
**上限の目安として1桁パーセント**と読むのが妥当である。

**本書は「剰余金の配当」をそのまま採る前提で書いている。** ⑥ は「現行の配当を
何年維持できるか」を見る指標であり、実際の現金支出を分母に置くほうが素直だと判断した。
代替案（`一株配当 × 株数`）は**株数の取得手段が無い**（IRバンクの JSON に株数の列は無く、
`株主資本 ÷ BPS` は概算にしかならない）ため、現時点では選べない。

### 10-2. 🟡 財務ブロックが丸ごと欠けている銘柄の挙動を明記していない

`src/infra/irbank/parse-fy-data.ts:435` は

> 財務は BPS（⑨ PBR）にしか使わない。欠けていても取り込みは成立させる

として `balance = null` を許容している。**本書の実装後、このコメントは古くなる**
（財務ブロックは負債総額にも使われる）。挙動としては「`totalLiabilities` を `null` に
して取り込みは成立させる」で既存方針と一貫するが、§2.3 に明記していない。
実装時に §2.3 へ1行足し、`parse-fy-data.ts` のコメントも直すこと。

### 10-3. 🟡 決算期変更（変則決算）に対応していない

本書は財務・配当の各ブロックから**独立に**最新実績年度を採る。決算期変更で
9か月などの変則決算が挟まると、**変則期間の配当総額（年額より少ない）を
「年間の配当総額」として採り、⑥ が維持可能年数を過大に出す。**

[market-data-source.md §8-5](./market-data-source.md) は同じ問題を
「決算月は全期間一定と仮定する」で回避しているが、本書は仮定すら置いていない。
`parse-fy-data` が落とすのは**同一 `fiscalYear` の重複行**だけなので、
`2025/03` → `2026/12` のように年度キーの月が変わるケースは検出されずに通る。

なお `ImportedFinancials.fiscalYearEndMonth`（`financial-source.ts:85`）は
既に「月が2つ以上現れたら `null`」を返す。**この値を見て集計を止める**のが
自然な対処だが、本書の範囲では未着手とした。

### 10-4. 🟡 採用した決算年度をどこに表示するか決まっていない

§2.3 は「年度を画面に出して人が判断する」と書き、`ImportedAmount.fiscalYear` を
そのために持たせている。しかし `BalanceSheetSnapshot`（`company.ts:33`）は年度を持たず、
**貸借対照表4欄の画面設計（どこに「2026年3月期」と出すか）は未着手**である。
[import-review.md](./import-review.md) にも該当する節が無い。

UI 設計は本書の範囲外（§1.1）だが、**引き渡し先が決まっていない**。
実装時に `import-review.md` へ節を足すか、`new-screen-spec` を起こすかを選ぶこと。
年度を出さないまま実装すると、§2.3 で「年度ずれを人が判断する」と決めた前提が
画面上で成立しない。
